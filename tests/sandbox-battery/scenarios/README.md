# Sandbox battery: scenarios

One script for each check that runs with `kubectl` and `helm`. The checks that go through the Rust adapter are described in `rust-checks.md` and implemented in `../rust` (its README lists which test covers which check). The scripts follow the real names of chart `br-sandbox-chart` 0.2.4, except the scripts `s05` and `s16` to `s23`, which need a cluster with chart 0.4.0 or later installed (the policy `br-sandbox-pod` with 21 rules and two bindings, and the `SandboxPool` resource). `run-all.sh` runs those scripts only when `CHART_VERSION` is 0.4.0 or later: with a lower version it records one row for each of them with the status `skip` (`{script}-chart-version`, never a pass), and a script named on the command line then records a failing check. A `CHART_VERSION` that is not three numbers (a suffix after `-` or `+` is allowed) gives the failing check `chart-version-valid` and the run stops before any script, so a mistyped version cannot skip scripts and end green. Set `CHART_VERSION` to the installed chart version before a run (the chart README is the contract; `../chart.sh fetch` pulls it, `../chart.sh install` installs it with `../values-test.yaml`). Every name that comes from the chart is in `names-chart.env`. Run all: `./run-all.sh`. Run some: `./run-all.sh s05-admission s07-egress-namespace`.

## Pod policy scripts

- The API server reports one rule of the policy in a refusal, the first one in the list of the policy that denies the pod (read from the Kubernetes source of the admission plugin; not proved by these scripts). A pod is judged by the API validation first, then by the policy. This decides what each check can show:
  - hostNetwork, hostPID and hostIPC: the API validation refuses them when `hostUsers` is false, so the pod also sets `hostUsers` true, and the rule `BR_SANDBOX_USERNS_REQUIRED` (listed before `BR_SANDBOX_HOST_NAMESPACE`) refuses it too. The expected set of these three checks is `HOST_NAMESPACE|USERNS_REQUIRED` (`CODES_HOST_SHARING`). The host rule alone is proved by the hostPort checks and by the isolated-rule check of `s21`. If the chart lists the host rule first, narrow `CODES_HOST_SHARING` to `HOST_NAMESPACE`.
  - Ephemeral containers (`s05`): the rule `BR_SANDBOX_IMMUTABLE` is listed before `BR_SANDBOX_EPHEMERAL_CONTAINERS` and also refuses a changed `ephemeralContainers`, so the check accepts both codes. The same holds for the checks of `s20`.
  - A Windows host process pod needs hostNetwork true and hostUsers true, so `BR_SANDBOX_USERNS_REQUIRED` is the first denied rule. The API server reports the first denied rule only, so the check accepts `USERNS_REQUIRED` or `WINDOWS_HOST_PROCESS` (`CODES_WINDOWS_HOST_PROCESS`).
- The policy has 21 rules. Six rules were added to the first fifteen: probe and hook hosts, `procMount`, AppArmor, SELinux, sysctls and the Windows host process. The sysctl rule allows the 12 safe sysctls only. The expected codes are in `names-chart.env` (`POD_RULE_CODES`) and in the variables `CODES_PROBE_HOST`, `CODES_HOOK_HOST`, `CODES_PROC_MOUNT`, `CODES_APPARMOR_FIELD`, `CODES_APPARMOR_ANNOTATION`, `CODES_SELINUX_CONTAINER`, `CODES_SELINUX_POD`, `CODES_SYSCTL` and `CODES_WINDOWS_HOST_PROCESS`, which can be set in the environment. A pod that is accepted never counts as a pass, and a refusal by a cause that is not in the expected set (the API validation, Pod Security, another rule) never counts as a pass. The checks against the live policy accept the code of an earlier rule where the list above says so (host sharing, ephemeral containers, Windows host process); the own-code proof of the host sharing rule, the ephemeral container rule and the Windows host process rule is the isolated-rule check of `s21`. A refusal of the API server for a feature that the cluster does not have (for example `procMount` Unmasked without its feature gate) shows in the detail of the check.
- `procMount`, restartable init containers (probes, hooks and ports of an init container need `restartPolicy: Always`) and the AppArmor field need a Kubernetes version that has them.
- Pod Security runs before the pod policy on a namespace that carries the label `pod-security.kubernetes.io/enforce`, and it can refuse a pod before the policy and hide its `BR_SANDBOX_*` code. The chart puts this label (`baseline`) on the namespaces it renders, as a second barrier. At the start, `s16`, `s17`, `s19` and `s20` each remove this label from the one pool namespace of client `CLIENT_A` that they use (by exact name: mode `allow` for `s16`, `s17` and `s20`, mode `none` for `s19`) and write a set-up line in the log; this is not a check. The label is put back when the scenario ends. `s17` ends with one row on its namespace with the label `baseline` set again. `s18` and `s21` do not touch the label (`s21` makes its own unmanaged namespaces). If the label cannot be read at the start, nothing is changed and the scenario records the failing check `pod-policy-set-up` and stops.
- Container kinds: the container-level items of `s16` and `s17` run on the agent container and on an init container, and the items that an ephemeral container can carry run on an ephemeral container in `s20`. Ports, probes and hooks do not exist on an ephemeral container (the API has no such field there), so the hostPort, probe and hook items have no ephemeral form. Items that belong to the pod (hostNetwork, hostPID, hostIPC, the sysctls, the AppArmor annotation, the pod-level AppArmor, SELinux and seccomp settings, the Windows host process at pod level, the hostPath volume) have no container kind. The item rules read the containers and the init containers only, so an ephemeral container is judged by the rule against ephemeral containers, not by the item rules.

## Scratch pools

`s22` and `s23` make their own pool, because a test that changes the image of a pool must not change the pool of another scenario, and on chart 0.4.0 the image is a field of the `SandboxPool` resource. The set-up is in `common-scratch.sh` (`scratch_pool_make`, `scratch_pool_accepted`, `scratch_pool_remove`):

- The namespace is named `{namespace of CLIENT_A in mode none}-bt22-{id}` or `-bt23-{id}`, so its name starts with the scope of the reference namespace (the policy `br-sandbox-namespace` demands a scope and a dash). It gets the labels of the reference namespace that start with `br.sandbox/` or `pod-security.kubernetes.io/`.
- The fence objects (ServiceAccount `sandbox`, ResourceQuota `br-sandbox-quota`, LimitRange `br-sandbox-limits`, NetworkPolicy `br-sandbox-default-deny`, ConfigMap `br-sandbox-pod-template`, RoleBinding `br-sandbox-keeper`; the list is `FENCE_COPIES`) are copied by `jq` from the reference namespace, without uid, labels and annotations. If the stamper of the platform makes them within 10 s, the script copies only the missing ones. The policy `br-sandbox-fence` refuses these writes unless the user is in `grants.writers` of the release, so the namespace and the copies are made with `kubectl --as=$FENCE_WRITER --as-group=$FENCE_WRITER_GROUP` (default `system:admin` and `system:masters`; set `FENCE_WRITER` to an identity of `grants.writers`). When the write is refused the script records a failing check with the API message and stops: the precondition is that identity.
- The `SandboxPool` is named `SANDBOX_POOL_NAME` (default `pool`); its `spec` is the `spec` of the same object in the reference namespace (the size), without `floors`, with the image of the scenario, `minReplicas` 1, `maxReplicas` 1 and `margin` 0. The script waits for `Accepted` `True` for 120 s before any measure, and records a failing check with the conditions when it does not come.
- At the end (also on failure, from the cleanup hook of the scenario) the script deletes the `SandboxPool` and then the namespace, each by its exact name, and only when the namespace was made. It waits up to 180 s and records `bt22-scratch-removed` or `bt23-scratch-removed`: a pass only when `kubectl get namespace` answers `NotFound`; a failing check, with the name, when the delete is refused, when the namespace stays, or when `kubectl` fails with any other error (the state is then not known). A refused delete of the pool records `bt22-scratch-pool-delete` or `bt23-scratch-pool-delete`.

## Rules of the scripts

- Timed scripts (`m-*`) run one at a time: `run-all.sh` takes the lock directory `TIMING_LOCK`. Each `record` adds the load average. A `TIMING_LOCK_WAIT_SECONDS` that is not a whole number of 1 or more records the failing check `timing-lock-wait-valid` and stops the script (or `run-all.sh`) at once. A script that cannot take the lock within `TIMING_LOCK_WAIT_SECONDS` (default 21600) records the failing check `timing-lock` and stops; the shell lock has no take-over (it holds no process id), so after a script that was killed, remove the folder by hand.
- `run-all.sh` counts pass, fail and skip from the `check` calls (`SCENARIO_TALLY`); only a fail changes the exit code, and a skip is never counted as a pass. A script that exits non-zero with no failing check recorded, a script that records no check, and a script name that is not in its lists each give a failing check.
- A negative check (a connection that must fail) runs through `probe_open_to` or `probe_count_to` (`common-probe.sh`): a failed exec, an empty output or a row count different from the number of targets gives `probe-failed`, never 0. Each negative row has a positive control from the same pod (`probe_control`: a loopback listener answers and `localhost` resolves; `s03` starts a listener in each pod).
- A measurement that has no sample, or fewer samples than planned, gives a failing `-ran` check.
- Scenario pods are claimed with a label change, as the adapter does. Pods that a script claims are deleted at its end.
- The check image (`sbx-battery-check:1`, `../check-image/Dockerfile`) adds `nc` to the `rancher/k3s` image; the chart check Job needs it.
- The pool image (`sbx-battery-agent:1`, `../agent-image/Dockerfile`) holds `python3`, `git` and `cargo`. The image contract (`/bin/sh`, `cat`, `find`) is proved in `rust-checks.md`.
- A pod that the runner cannot make (uid 0) is made with `kubectl --as=system:serviceaccount:sbx-system:br-sandbox-netcheck create`: the chart lets that identity make root pods (rule 10), and nothing else. No privileged pod is used for it.

## Chart layout the scenarios expect

The values file gives these (client, mode) pairs; the chart makes one namespace and one pool for each, with the pool id `{client}-{mode}` and the ReplicaSet `warm-{client}-{mode}` for a chart below 0.4.0; from 0.4.0 on the pool id is the namespace name (`sbx-{client}-{mode}`) and the ReplicaSet is `warm-sbx-{client}-{mode}`.

| Pair | Namespaces | Used by |
|---|---|---|
| `ca` `none`, `ca` `full` (no credential set) | `sbx-ca-none`, `sbx-ca-full`; no egress namespace | `s03`, `s04`, `s07`, `s08` |
| `cb` `none`, `cb` `full` (no credential set) | `sbx-cb-none`, `sbx-cb-full`; no egress namespace | `s03` |
| `ca` `allow`, `cb` `allow` | `sbx-ca-allow` + `sbx-ca-allow-egress`, same for `cb` | `s03`, `s04`, `s05`, `s07`, `s08`, `m-netpol-delay`, `m-window` |
| `canary` `allow` with one credential set | `sbx-canary-allow` + `-egress` | `s10` |
| `platform` `allow` with two credential sets | `sbx-platform-allow` + `-egress` | `s11` |
| `pivot` `allow` (names of the internal targets on the allowlist), `pivot` `full` with one credential set | `sbx-pivot-allow` + `-egress`, `sbx-pivot-full` + `-egress` | `s08`, `s13` |

- `egress.enabled: true`; `runner.service_account` and `runner.namespace` give `RUNNER_SA` and `RUNNER_NS` (the chart makes no runner ServiceAccount; impersonation with `--as` needs none). `keeper.enabled: true` with the image `ghcr.io/botresources/br-sandbox-keeper` by digest (`KEEPER_IMAGE` in `names-chart.env`), so the keeper starts and it manages the pool sizes and deletes warm pods older than `warm_max_age_seconds`; `network_check.image` has `sh`, `kubectl`, `nc`.
- The release namespace (`HELM_NAMESPACE`, default `default`) is not the system namespace: the chart renders the Namespace `sbx-system` itself.
- The pod quota is `max_sandboxes` plus `quota.extra_pods`.
- Proxy pods, the credential Secrets, the CA key Secret and the reload Secret live in the egress namespace only; `../chart.sh install` makes them after the chart. The proxy address in a sandbox is the fixed ClusterIP of the Service `br-sandbox-proxy` (`HTTPS_PROXY`), the CA certificate is the file `/etc/br-sandbox-ca/ca.crt`, the placeholders are in the variables of `credential_set.secrets[].env_name`.
- `s07` makes its own test pod with `br.sandbox/role=proxy` in the egress namespace (stand-in listener on the tunnel port, on the four loopback ports of the proxy and on 80 and 443), so the network rules and the rights are proved on a pod that listens on every port; the pod declares no container port. It is deleted at the end.
- The chart check Job (`br-sandbox-netcheck-{run_id}`) fails when a probe reaches the tunnel port of an own proxy; `s04` counts that path apart (pod address and ClusterIP) and fails on every other mismatch.
- The local image `sbx-battery-agent:1` is not kept in the Docker store after the last row that needs it (`s01` uses it for the plain `docker run` side); the node holds it. Rebuild it from `../agent-image/Dockerfile` before a rerun of `s01`.
- The proxy denies internal addresses and resolves only through `network.public_resolvers`. The test servers are Docker containers outside the pod, service and node ranges; their names are resolved by the DNS stub; the proxy trusts the test CA through `egress.proxy.upstream_ca` (ConfigMap `sbx-test-ca`).

## Assumptions on the set-up

`s22` needs the variables `MOVING_IMAGE` (the image as the pool pulls it), `MOVING_PUSH` (the same image as the docker of the host pushes it) and `BASE_IMAGE` (the image to build from), the same as the Rust tests of `../rust` (its README), a `docker` of the host that is logged in to that registry, and a node that pulls from it; the set-up of this folder does not make a push path, and a missing variable or a refused push gives a failing check that names it. `s23` needs `MOVING_IMAGE` or `ABSENT_IMAGE`. Both need the release to be chart 0.4.0 or later with the keeper that serves `SandboxPool`, and `s22` needs `warm_max_age_seconds` of 300 or less in the keeper document.

The creds file gives `GITEA_TOKEN`, `S3_*`; the chart exposes the names of `names-chart.env`; the agent image and the check image are loaded in the node; the tools image, the proxy image and the keeper image are pulled by digest. The Secret `store-credentials` of the system namespace holds `S3_ACCESS_KEY` and `S3_SECRET_KEY` of the creds file as `AWS_ACCESS_KEY_ID` and `AWS_SECRET_ACCESS_KEY` (made by `../chart.sh install`).
