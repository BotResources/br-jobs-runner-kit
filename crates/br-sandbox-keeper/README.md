# br-sandbox-keeper

The controller of the sandbox pools of `br-runner-sandbox`. It reads the `SandboxPool` resources, makes the pool ReplicaSet `warm-{namespace}` of each one in a fenced namespace, sizes it from the rate of claims, replaces its stale warm pods by steps, deletes the pods that are old or idle or stuck or failed, writes the condition `WarmPodsFailing` on the pool ReplicaSet and the status of each resource, and deletes the saves, records and tombstones that have expired. The package has a library and a binary. The binary loads the configuration and runs the library until it gets the stop signal.

**Compatibility.** Keeper 0.2 does not work with chart 0.3.x or earlier: it refuses the `pools` configuration at start. Chart 0.3.x needs keeper 0.1.x.

## Install

```toml
br-sandbox-keeper = { git = "https://github.com/BotResources/br-jobs-runner-kit", package = "br-sandbox-keeper", tag = "br-sandbox-keeper/v0.2.1", version = "0.2.1" }
```

The crate takes the names of the labels, the annotations, the pool condition and the store keys from `br-runner-sandbox`, except the annotation `{label_prefix}/template-hash`, which the crate names itself, and a crate that names the types of that sibling must reach it through the same git url and the same tag string. The image `ghcr.io/botresources/br-sandbox-keeper` holds the binary and the system root certificates, and its tag is the version of the crate.

## Run

The binary reads one JSON document at the path in the variable `BR_SANDBOX_CONFIG`, and the credential of the object store from the variables `AWS_ACCESS_KEY_ID` and `AWS_SECRET_ACCESS_KEY`. The credential is not part of the document, is never logged, and is not shown by `Debug`. The keeper reads no Secret through the Kubernetes API. The logs are JSON lines on the standard output; they hold the keys of objects and the names of pods, never the content of an object. The binary ends with a failure code when the library returns an error, and with the code 0 after SIGTERM or an interrupt.

The binary runs as 2 replicas. The identity of a replica for the Lease is its `HOSTNAME` with a unique suffix. The Lease namespace is `lease_namespace`, or the namespace of the pod when the key is not set.

## The resource `SandboxPool`

`resource` holds the type of the custom resource and the definition that the type gives. The resource is `sandboxpools.sandbox.botresources.ai`, kind `SandboxPool`, version `v1alpha1`, namespaced, with a `status` subresource and no `scale` subresource, and the printer columns `Desired`, `Ready`, `Accepted` and `Age`. `v1alpha1` can change with no conversion and with no promise.

- `SandboxPool` is `metadata`, a raw `spec` (a JSON value) and an optional `SandboxPoolStatus`; it implements `kube::Resource`. The `spec` is not parsed when the object is read, so one resource with a bad spec never fails the list or the watch that holds it. `SandboxPool::read_spec` parses it strictly into `SandboxPoolSpec` and gives `SpecError` (the text of the parser, which names the key) when it cannot; `SandboxPool::new` builds a resource from a `SandboxPoolSpec`.
- `SandboxPoolSpec` has `image`, `size` (`PoolSize`: `cpu`, `memory` and `disk`, each a `SizeBounds` with `request` and `limit`), `minReplicas`, `maxReplicas`, `refillSeconds` (default `DEFAULT_REFILL_SECONDS`, 3), `margin` (default `DEFAULT_MARGIN`, 2) and `floors` (a list of `FloorSpec`: `from`, `to`, `floor`; default empty). `image`, `size`, `minReplicas` and `maxReplicas` are required. The read is strict: a key that the type does not know is refused at the spec, in `size`, in each of `cpu`, `memory` and `disk`, and in each item of `floors`; a value of the wrong type is refused and never repaired. `MAX_FLOORS` (16) and `MAX_TIME_LENGTH` (64) are the bounds that the definition carries.
- `read_spec` checks the shape only, and the definition holds the four rules below. The other rules of the resource (a request not above its limit, the form of a time of day, the quantities above zero, the bounds) are checked by the keeper with `pool::validate` at each evaluation of the pool; a resource that fails them is `Accepted=False` with `InvalidSpec`.
- `definition()` builds the `CustomResourceDefinition` and `definition_yaml()` writes it as YAML. The file `definition/sandboxpools.yaml` is that text, and a test holds the file equal to the output of the function (regenerate it from `definition_yaml()`). The definition marks `x-kubernetes-preserve-unknown-fields` on `spec`, `spec.size`, `spec.size.cpu`, `spec.size.memory`, `spec.size.disk` and the items of `spec.floors`, and on `status`, so that the API server keeps an unknown key and the strict read of the keeper sees it. Without the mark, a strict create and a server-side apply refuse an unknown key, and a create with validation off drops it. With the mark, the key is kept at `spec`, `spec.size`, `spec.size.cpu`, `spec.size.memory`, `spec.size.disk` and the items of `spec.floors`; the leaves `request` and `limit` are strings, so an object there is refused. It bounds `floors` at 16 items and `from` and `to` at 64 characters, which a rule over the items needs. It requires `image`, and `minReplicas` and `maxReplicas` are integers from 0.
- The CEL rules of the definition are four, all on `spec`: `minReplicas` is not above `maxReplicas`; `image` is present and holds a character that is not white space, written `self.image.matches('\\S')`; a transition rule that `image` does not change to a value that holds no such character; a window of `floors` has `from` not equal to `to`. The definition refuses an empty or white-space-only image. In the RE2 engine of the API server `\S` matches any character except space, tab, line feed, form feed and carriage return; so the definition refuses an image made of these characters only. A vertical tab and the white space characters outside ASCII (for example U+00A0) match `\S`, so the definition accepts an image made of them; the keeper does not (`pool::validate` trims with the Unicode definition of white space and gives `InvalidSpec`). The definition holds no other rule. In particular it has no rule that a request is not above its limit. The keeper keeps its own check of every rule, with `pool::validate` at each evaluation of the pool, and that check is the guarantee for every rule; the rules of the definition only refuse early. The test of the repository does not evaluate the rules; it holds their text equal to the text of the file.
- The checked-in definition was applied to a real API server (Kubernetes v1.33) and its rules were exercised there: the four rules, the bounds, the preserve mark (create, create with validation off, strict create, server-side apply and merge patch) and the image rows. These checks are not tests of this repository: its tests hold the text of the file equal to the text of the function, and no test applies the file to an API server. The `\S` form is ASCII only, as stated above: a vertical tab and non-ASCII white space pass the definition and the keeper refuses them.
- The schema has `minimum: 0` (written `0.0` by the serializer) on `minReplicas` and `maxReplicas` only; the other numbers are `integer` with no bound, and the keeper type (`u32`) refuses a negative one.
- The schema keywords beyond the CEL rules are: `minimum: 0` on `minReplicas` and `maxReplicas`; `required: [image]` on `spec`; `x-kubernetes-preserve-unknown-fields: true` on `status`, with the marks on `spec` named above; `maxItems: 16` on `floors`; `maxLength: 64` on `from` and `to`. `image` has no length bound.

## Rights table

`RIGHTS` is the table of the rights of the keeper as data, one `Right` for each row: the `scope` (`RightScope::EachManagedNamespace`, `LeaseNamespace` or `Cluster`), the `api_group`, the `resource` (a sub-resource is written `resource/sub`), the `resource_names` (empty, except `configmaps`, which is the one name `POD_TEMPLATE_CONFIGMAP` = `br-sandbox-pod-template`) and the `verbs`. A test holds the table equal to the rows written in that test, row by row, and that no row has a wildcard, `escalate`, `bind`, `impersonate`, or a write on `networkpolicies`, `namespaces`, `roles`, `rolebindings`, `clusterroles`, `resourcequotas` or the admission policies. The status right is `patch` on `sandboxpools/status` only, and the table has no right on `roles`, `secrets`, `pods/exec` or a finalizer. The table is what the keeper is granted and not what this version calls: the calls that this version makes are a subset of it, and the rights test of the client holds them to it. A chart renders its Roles from this table. `NETWORK_POLICY_NAMES` is the closed list of the names of a network policy of a sandbox namespace (`br-sandbox-default-deny`, `br-sandbox-egress-allow`, `br-sandbox-egress-full`); the cluster I/O layer reads the network policies of a namespace (see "Cluster I/O layer").

## Cluster I/O layer

`cluster` holds every call of the keeper to the Kubernetes API, behind two sealed traits: `KubeApi` (pods, ReplicaSet replicas and condition, events, the Lease) and `PoolApi` (a supertrait of `KubeApi`: the watches of namespaces, bindings and resources, the readers of the fence and of the template, the writes of a pool). `KubeCluster` implements both on a `kube` client. The rights test of the client drives every call against a stub API server and holds the verb, the resource, the name (the template ConfigMap) and the scope (cluster-wide only for `namespaces` and `validatingadmissionpolicybindings`) to `RIGHTS`; the keeper makes no call outside the table.

- **Views.** `Views::run` holds one watch of the namespaces that match `managed_namespace_selector` (the selector is the label selector of the list and of the watch), one cluster-wide watch of the binding `br-sandbox-pod` (a field selector on its name), and, for each managed namespace, one watch of pods and one of `SandboxPool` resources. A namespace that leaves the selector loses its watches and its views. Each view (`View`) has a synced flag: it is false before the first list, it is false after a failed list, a watch that cannot be opened or reopened, a broken watch or an error event, and it is true again only when the next list arrives. A read of a view that is not synced is `Read::NotObserved` with the reason, never an empty answer. `Views::subscribe` gives a counter that changes at each event, and `Views::notices` gives the stream of `Notice` values (a pod event of a namespace, or a change of a watch of namespaces, bindings or resources with its failure, if any) that the controller reads. A list that answers 404 is `ViewEvent::Missing`: the view is absent and not synced, and `Views::not_ready_reason` says that the definition of the resource is absent.
- **Readers.** `Observer::fence` reads the labels of the namespace and the binding from the views, the quota `br-sandbox-quota` by name and the network policies of the namespace, and gives `FenceInputs` (whose `verdict` calls `pool::fence_verdict`), `FenceObservation::NotManaged` for a namespace outside the selector, or `FenceObservation::NotObserved` with the reason when a view is not synced or a read failed. `Observer::template` reads the ConfigMap `br-sandbox-pod-template` (one `get`) and gives the result of `PoolTemplate::read`; a ConfigMap that is absent is `TemplateFault::Absent`, and a failed read is `NotObserved`. `Observer::replica_set` gives `ReplicaSetRead::{Absent, Owned, NotOwned}` through `pool::check_ownership`.
- **Writers.** `PoolWriter` is the only way to write: it creates the ReplicaSet `warm-{namespace}` (the owner reference of the resource with `controller: true`, no `blockOwnerDeletion`, no finalizer; the body is built from the JSON of the template, so a field of the template that this version of `k8s-openapi` does not know is kept); changes `spec.replicas` by a server-side apply of that one field under the field manager `br-sandbox-keeper`, only when a fresh read of the ReplicaSet says the value differs; applies `spec.template` only, by a server-side apply under the field manager `br-sandbox-keeper-template`, when the hash annotation differs, or when the hash is current and the managed fields of the ReplicaSet hold no template applied under `br-sandbox-keeper-template` (a ReplicaSet with no managed fields at all is judged by the hash alone; see Field managers and Upgrade from 0.2.0); deletes the ReplicaSet with the uid as precondition; deletes a pod with the preconditions `uid` and `resourceVersion`; and patches `sandboxpools/status` (a merge patch on the status subresource, with `null` for each status field that has no value, so that a field with no observation does not keep an old value; the keeper never reads the status subresource). Before each write on a ReplicaSet it reads the ReplicaSet and checks that it is in the namespace, has the name, is not in deletion and has the controller reference of the resource (group, kind and uid; the version does not count): else the call is `WriteError::NotOwned` and nothing is written. A call that the server refuses with 403 is logged, counted in `br_sandbox_keeper_sweep_errors_total` and returned as `WriteError::Refused`; the caller tries again. The call `PoolWriter` makes is not retried by the writer, and the writer does not check that a view is synced: that check belongs to the caller.
- **Field managers.** A ReplicaSet of a pool has these entries of managed fields from the keeper. `br-sandbox-keeper` with the operation Update owns the fields that the create wrote, until another manager takes a field with a different value. `br-sandbox-keeper` with the operation Apply owns the one field `spec.replicas`. `br-sandbox-keeper-template` with the operation Apply owns `spec.template`. The condition `WarmPodsFailing` is a server-side apply on the status subresource under `br-sandbox-keeper`, which has its own entry. The two applies on the main resource use two managers because a server-side apply removes the fields that the same manager applied before and that its new body no longer holds: with one manager, the apply of the replicas removed the template that the same manager had applied, the API server then refused the write with 422 (`spec.template.spec.containers[0].image: Required value`) at each pass, and the pool could not change its size; the apply of the template would likewise have removed the replicas. Keeper 0.2.0 had this fault: after a change of the template (an edit of the image, of the size or of the template ConfigMap) followed by a change of the replicas, the ReplicaSet lost template fields. The fault is the loss of any field that the template apply had set to a value different from the one of the create, not only the image. When the image was lost, the API server refused each write of the replicas with 422 and the pool could not change its size. When only optional fields were lost (for example the cpu and memory requests of the agent container), the API server accepted the write, and the ReplicaSet made no pod because the admission policy refused it (`PodsRefused`).
- **Upgrade from 0.2.0, and the template write of each pool.** The template is in place only when its hash annotation is the current one and either the managed fields of the ReplicaSet hold an entry of `br-sandbox-keeper-template` with the operation Apply, on the main resource, with `spec.template`, or the ReplicaSet has no managed fields at all (absent, or an empty list). In every other case the keeper applies the whole rendered template once under `br-sandbox-keeper-template`, with `force`. So each pool gets one idempotent template write at its first evaluation by 0.2.1, on a hash that did not change: a ReplicaSet that keeper 0.2.0 wrote (its template fields may be owned by `br-sandbox-keeper` with the operation Apply alone, and such a ReplicaSet refuses the apply of the replicas even when its template is current), and a ReplicaSet that the keeper made with the create (the create is an Update entry, so it has no entry of the template manager). The rule reads the hash and the entry: the keeper writes the whole template when the hash annotation is not the current one, or when it is the current one, the ReplicaSet has managed fields and the template manager holds no template. So a ReplicaSet whose template manager holds no template gets one write of the whole template, and that write repairs a template that lost fields. A ReplicaSet whose template manager already holds the template is not written again, also when template fields were lost after that: the keeper does not repair this case until the hash changes. What a real API server does with the hash annotation when it removes fields is not observed; the tests build the state of a template that lost fields with a current hash by hand. The write keeps the hash annotation. The tests with warm pods of the current hash show that the write replaces no pod and starts no rollout. When stale warm pods are present, the write does not change the hash, so the rollout goes on by its own rule (steps of stale pods, not ready first, then the oldest) and the warm pods of the current hash stay. A write that fails or that the API server refuses is logged, counted in `br_sandbox_keeper_sweep_errors_total` and tried again after the retry period of the lease. The keeper still writes the replicas in that pass, but it makes no rollout step: for a pool whose hash did not change, the replacement of stale warm pods waits until the write goes through. After the write the entry exists, the fields are owned by both managers, the next apply of the replicas removes nothing of the template, and from then on the hash and the entry decide, so the template is written only at a change of the hash. The managed fields are read from the ReplicaSet that the keeper already reads before each write. When that ReplicaSet comes with no managed fields at all (absent, or an empty list), the keeper cannot see the entry: it judges by the hash alone and never writes at each pass, and a template that lost fields in that case is not repaired until its hash changes.

| `save_ttl_seconds` | age after which a save is expired | required |
| `skew_margin_seconds` | extra wait before the keeper deletes an expired save | 60 |
| `sweep_interval_seconds`, `sweep_page_size` | the pass over the store | 60, 1000 |
| `attempt_ttl_seconds` | age of an orphan attempt | 3600 |
| `tombstone_ttl_seconds` | age of a record or tombstone | 31 536 000 |
| `stuck_ttl_seconds` | cap on the age of a dirty claimed pod | 7200 |
| `failed_pod_ttl_seconds` | age of a Failed or Evicted pod | 300 |
| `warm_max_age_seconds` | maximum age of a warm pod, except a Pending pod that the scheduler marks Unschedulable, which is held and has no age deadline | 1800 |
| `pending_alarm_seconds` | time that a warm pod may stay Pending before the event | 60 |
| `rate_window_seconds`, `rate_bucket_seconds` | the window of the claim rate and the width of its buckets | 300, 10 |
| `scale_down_cooldown_seconds`, `scale_down_step`, `scale_down_step_interval_seconds` | damping of a scale-down | 120, 5, 10 |
| `lease_namespace`, `lease_duration_seconds`, `renew_deadline_seconds`, `retry_period_seconds` | leader election | namespace of the pod, 15, 10, 2 |
| `timezone` | time zone name of the floors of the day | `UTC` |
| `idle_ttl_seconds` | how long a saved pod stays bound when its state is not smaller than the threshold; the same for every pool | 120 |
| `idle_keep_min_state_bytes` | the threshold of the state size; the same for every pool | 10 000 000 |
| `agent_container` | name of the agent container of the pod template | required, no default |

The key `pools` is not a key of the keeper: a document that holds it (even as `null`) is a start fault. A pool is a `SandboxPool` resource.

A document is a fault when `save_ttl_seconds` is 0 or below; a duration that drives a timer is 0 (except `idle_ttl_seconds` and `skew_margin_seconds`); `rate_bucket_seconds` is above `rate_window_seconds`; `scale_down_step` is below 1; the Lease durations are not in the order `lease_duration_seconds` above `renew_deadline_seconds` above `retry_period_seconds`; the time zone is unknown; a required key is missing; or a key is unknown. The code also refuses: the key `pools`; a number below 0, or too large for its type; a text key that is blank; a `store_endpoint` that is not an http or https URL with a host and no user information; a `listen_address` that is not a socket address; a `label_prefix` that `br-runner-sandbox` refuses. The rules of a pool (sizes, quantities, floor windows) are checked on the resource by `pool::validate`.

## Labels and annotations

The keeper reads these names through the label prefix and takes them from `br-runner-sandbox`, except `template-hash`, which is its own name. It never writes a label or an annotation on a pod, never claims a pod, and never patches a pod. It writes one annotation, `{label_prefix}/template-hash`, in the pod template of the pool ReplicaSet.

| Role | Name | Kind | Use |
|---|---|---|---|
| pool state | `{label_prefix}/pool` = `warm` or `claimed` | pod label | which pods are warm or claimed; the claim rate |
| pool id | `{label_prefix}/pool-id` | pod label | the pool of a pod |
| thread, agent | `{label_prefix}/thread`, `{label_prefix}/agent` | pod labels | log fields only |
| clean or dirty | `{label_prefix}/clean` | pod annotation | idle or stuck |
| claimed-at | `{label_prefix}/claimed-at` | pod annotation | the clock of `stuck_ttl_seconds` |
| idle-since | `{label_prefix}/idle-since` | pod annotation | the clock of the idle deadline |
| state-bytes | `{label_prefix}/state-bytes` | pod annotation | the choice of `idle_ttl_seconds` or 0 |
| managed namespace | `{label_prefix}/managed` = `true` | namespace label | which namespaces the keeper serves |
| template hash | `{label_prefix}/template-hash` | pod annotation, written by the keeper in the pod template | which warm pods are stale (the SHA-256 of the canonical JSON of the template) |

The keeper serves every namespace that matches `managed_namespace_selector`. It holds a watch of the namespaces with that selector, so a namespace that gets the label is served as soon as the watch tells it, and a namespace that loses the label is dropped from service before any verdict: its watches end, its pods are forgotten, and nothing is deleted or written there (no ReplicaSet is deleted and no pod expires) until it matches again. It acts only on pods that carry the pool-state label with the value `warm` or `claimed`. A pod of a namespace that has no resource, or whose pool id is not the namespace, expires by the same rules, with `idle_ttl_seconds` and `idle_keep_min_state_bytes` of the keeper; it gets no sizing, no condition and no event, because the keeper knows no ReplicaSet for it.

A claimed pod whose annotation that its rule needs is missing or unreadable is never deleted by that rule. It is logged and counted in `br_sandbox_keeper_unreadable_pods`.

## Behaviour

- **Reconcile.** For each managed namespace the keeper holds one view of the pods and one view of the `SandboxPool` resources, and the views of the namespaces and of the binding `br-sandbox-pod`. A pool is judged when a resource or a pod of its pool changes, when the namespaces or the binding change, when the leadership is gained, at each rate bucket (`rate_bucket_seconds`) for every pool, and at the deadline that an earlier pass asked for. A namespace is judged for the first time only when its pod view, its resource view, the namespace view and the binding view have each synced once: before that the keeper writes nothing and no status. A pool is judged from the pod view of the keeper; the ReplicaSet and the template are read from the API server in the same pass.
- **Pool of a resource.** The pool id of a resource is its namespace and the pool ReplicaSet is `warm-{namespace}`. The order of the judgment is: `NotObserved` when the fence or the duplicate fact is not observed, the fence of the namespace (`NamespaceNotFenced`), the duplicate rule (`DuplicatePool`), the rules of the spec (`InvalidSpec`), then the template (read only when the namespace is fenced, the resource is not a duplicate and the spec is valid). A bad spec in a namespace that is not fenced is `NamespaceNotFenced`. When all hold the keeper creates the ReplicaSet if a read in the same pass says the name is free (a create that answers "exists" is a new read and never a second object), applies `spec.template` when its hash differs from the held one, or when the hash is current and the managed fields of the ReplicaSet hold no template applied under `br-sandbox-keeper-template` (see "Upgrade from 0.2.0, and the template write of each pool"), sets the replicas, raises `PoolAtMax`, and runs the rollout. It never writes a ReplicaSet that the resource does not own: no write, `Ready=False` with `ReplicaSetNotOwned`. A new resource with a bad rule makes no ReplicaSet; a bad edit of a resource that has one freezes it (no resize, no change of the ReplicaSet, no rollout), and `observedGeneration` is the bad generation. The same holds for `TemplateAbsent` and `InvalidTemplate`. The expiry of pods and the condition `WarmPodsFailing` go on for a pool that is frozen, invalid, duplicated, unfenced or deleted. A second resource of a namespace is `DuplicatePool` and nothing is changed for it. When a resource is deleted the API server deletes its ReplicaSet and the keeper writes nothing for it.
- **Fence.** The namespace must hold the quota `br-sandbox-quota`, hold the default-deny network policy `br-sandbox-default-deny` (empty pod selector, types Ingress and Egress, no allow rule), hold no network policy outside the closed list, and be selected by the binding `br-sandbox-pod`. When the keeper observes, on synced views and with every read good, that a namespace with a pool is not fenced, it deletes the ReplicaSet that the resource owns (with the uid as precondition, after the ownership check) and the status says `Accepted=False` with `NamespaceNotFenced` and the object that is missing. It never does this from a view that is not synced or from a read that failed: then it writes nothing and `Accepted` is `Unknown` with `NotObserved`. The claimed pods are not deleted for this reason. When the fence is back the keeper makes the pool again. The Role of the keeper is not an object of the check. The verdict of the fence still names `NotSelected` for a namespace that the selector does not match, but that verdict is not reached for a namespace that left the watch: a namespace that loses the managed label is dropped from service before any verdict and nothing is deleted there (see "Not guaranteed").
- **Pool size.** `desired = clamp( max( ceil(peak_claim_rate × refill_seconds) + margin, floor_now ), min_replicas, max_replicas )`, in integer arithmetic. The peak claim rate is the highest bucket of `rate_bucket_seconds` in the last `rate_window_seconds`. A claim is a pod that changes from `warm` to `claimed`, or a pod that appears already `claimed` with no owner and is not older than the window. Each replica counts the claims from its own watch. A scale-up is applied at once. A scale-down is applied only after `desired` has stayed below the replicas for `scale_down_cooldown_seconds`, then by at most `scale_down_step` each `scale_down_step_interval_seconds`. The keeper writes `spec.replicas` by server-side apply under the field manager `br-sandbox-keeper`, only when the value differs from a fresh read, and raises `PoolAtMax` once for each transition into a size above `max_replicas`. The keeper adds no cap on `maxReplicas`: the quota of the namespace and the admission policy are the only bound, and `PodsRefused` shows a refusal.
- **Rollout.** A ReplicaSet does not replace its pods when its template changes. After the keeper applies a new template (a change of the image, of the size or of the ConfigMap, seen at each evaluation of the pool), `rules::plan_rollout` picks the stale warm pods (the pods that are not Ready first, then the oldest first), at most `scale_down_step` of them, and the keeper deletes them with the preconditions of the expiry rules. The next step starts only when every warm pod of the current template is Ready (`Wait::CurrentPodNotReady`) and the pool again holds as many warm pods as its replicas (`Wait::ReplacementsMissing`). The rollout stops while a warm pod of the current template fails. It also makes no step in a pass where the template write fails or is refused, until a later pass where the write goes through. A claimed pod is never deleted by a rollout, a pod of the current template is never stale, and the metric `br_sandbox_keeper_pods_deleted_total` counts these deletes with the reason `rollout`. A stale warm pod ends at `warm_max_age_seconds` whatever the rollout does, except a Pending pod that the scheduler marks Unschedulable, which is held. A warm pod whose template hash is missing or unreadable is never judged stale; it is counted in `br_sandbox_keeper_unreadable_pods`.
- **Pod expiry.** One rule for each state, as a pure function of the pod: a warm pod at `creationTimestamp + warm_max_age_seconds`, except a Pending pod that the scheduler marks Unschedulable, which is held (it has no age deadline, a rollout step may take it, and the alarm below still applies to it); a clean claimed pod at `idle-since + ttl` (`idle_ttl_seconds` when `state-bytes` is not below the threshold, 0 below it); a clean claimed pod with no `idle-since`, and a dirty claimed pod, at `claimed-at + stuck_ttl_seconds`; a Failed pod `failed_pod_ttl_seconds` after the keeper first saw it so. A warm pod that is Pending and not failing raises `WarmPodsPending` once for each pod after `pending_alarm_seconds`. A delete carries the uid and the resourceVersion of the last read; on a conflict the pod is read again and judged again, and a pod that is gone is not an error. A pod of a namespace whose resource is deleted or frozen, or whose namespace lost its fence, still expires by these rules, with the values of the keeper.
- **Failing pool.** The condition `WarmPodsFailing` on the status of the pool ReplicaSet is `True` when a warm pod that has not been Ready (as far as the memory of the replica goes, see "Not guaranteed") has a container with a pull failure (`ImagePullFailing`) or a crash at start (`StartCrashing`), and `False` otherwise, with the reason `NoWarmPodFailing` and an empty message; it is written `False` at the first judgement. `lastTransitionTime` changes only when the status changes. The same condition is part of the status of the resource, and one function builds both.
- **Status.** Only the leader writes the status of a resource. It has the conditions `Accepted` (`Valid`, `InvalidSpec`, `NamespaceNotFenced`, `DuplicatePool`, `TemplateAbsent`, `InvalidTemplate`, or `Unknown` with `NotObserved`), `Ready` (`True` with `WarmPodsReady` when the Ready warm pods are `minReplicas` or more; `False` with `ReplicaSetAbsent`, `ReplicaSetNotOwned`, `WarmBelowMinimum` or `PodsRefused`; `Unknown` with `NotObserved`) and `WarmPodsFailing`, the counts `desiredReplicas`, `replicas`, `readyReplicas` and `updatedReplicas`, `observedGeneration` and `observedAt`. A write happens when a value changes and at most once in 5 seconds for each pool. A count comes from a pod view that is synced; when a view is not synced or a read failed, the keeper writes no ReplicaSet and the status says `Unknown` with `NotObserved`.
- **Saves.** Every `sweep_interval_seconds` the leader lists `saves/` in pages of `sweep_page_size` and reads the `made_at` of each manifest. A save is expired when `now - made_at` is above `save_ttl_seconds + skew_margin_seconds`. For one expired save the order is: write the tombstone (`expired_at = made_at + save_ttl_seconds`, a pure function of the manifest), delete the manifest, delete the parts of every attempt, leave the record. An attempt that no manifest names is an orphan once its newest object is older than `attempt_ttl_seconds`. A record or tombstone is deleted when `tombstone_ttl_seconds` has passed since its end time (its start time when it has no end time) or, for a tombstone, since its `expired_at`; the time that the store gives an object never decides. The sweep lists `records/` and `tombstones/` and reads every listed object on every sweep, as it reads every manifest. An object that cannot be read, or that holds no readable time, is never deleted for age; it is logged with its key and counted in `br_sandbox_keeper_sweep_errors_total`. The keeper writes only under `tombstones/`, and `GuardedBucket` refuses any other write or any key outside `saves/`, `records/` and `tombstones/`.
- **Watches.** The keeper holds one watch of pods and one watch of resources for each managed namespace, a watch of the namespaces that match the selector, and a watch of the binding; it holds no cluster-wide watch of pods. A list that fails, a watch that cannot be opened or reopened, a watch that breaks and an error event each give a log line at the error level with the namespace and the reason, and count once in `br_sandbox_keeper_sweep_errors_total`. The keeper then waits one second and lists again, so the next list repairs the view. While a pod view is not synced the keeper writes no ReplicaSet for that namespace and the status says `NotObserved`; the pods it holds stay judged by the expiry rules.
- **Leader election.** A Lease named `br-sandbox-keeper`. Both replicas keep their watches; only the holder writes (replicas, condition, events, pod deletes, tombstones, object deletes). A write is refused once `renew_deadline_seconds` has passed without a renewal. A Lease read or write that fails is logged at the warn level, counted in `br_sandbox_keeper_sweep_errors_total` and tried again after `retry_period_seconds`; a leader keeps the lead until `renew_deadline_seconds` has passed without a renewal. A write that is refused because another writer changed the Lease (a conflict) is logged at the info level and is not counted.
- **Endpoints.** `/livez` answers 200 while the process runs. `/readyz` answers 503, with the reason in the body, until the namespace view, the binding view and the pod view and the resource view of each managed namespace have each done a first full sync, while the store check of the start has not passed, and while the definition of the resource is absent (a list of `SandboxPool` that answers 404). A cluster with no managed namespace, or with no resource, is ready. The keeper never creates the definition and never creates the bucket. After the first sync, a watch that breaks does not make the keeper not ready; only the absent definition does, and it is ready again when the definition is back. `/metrics` answers in the Prometheus text format: `br_sandbox_keeper_pool_desired`, `_pool_warm_ready` and `_claims_per_second` (each with the label `pool`, the name of the namespace, one series for each namespace that has a resource), `_idle_pods` (no label: the number of claimed pods whose clean annotation is `true`, in every managed namespace), `_pods_deleted_total` (label `reason`: `warm_max_age`, `idle`, `stuck`, `failed`, `rollout`), `_saves_deleted_total`, `_tombstones_written_total`, `_orphans_deleted_total`, `_sweep_errors_total`, `_unreadable_pods`, `_is_leader`. The events are `PoolAtMax` and `WarmPodsPending`, on the ReplicaSet of the pool. No other event.

## Rights

The table above is the grant. What this version calls, in each managed namespace: `pods` get, list, watch, delete; `replicasets` get, create, patch, delete; `replicasets/status` patch; `events` create; `sandboxpools` list, watch; `sandboxpools/status` patch; `configmaps` get (the one name `br-sandbox-pod-template`); `resourcequotas` get; `networkpolicies` list. In the Lease namespace: `leases` get, create, update. Cluster-wide: `namespaces` list, watch; `validatingadmissionpolicybindings` list, watch. No `pods/exec`, no `pods/patch`, no `secrets`, no right on a finalizer. A call that the API server refuses for a missing right is an action that fails: it is logged, counted in `br_sandbox_keeper_sweep_errors_total` and tried again. When the refused call is a write of a ReplicaSet (create, replicas, template, condition, delete) or a delete of a pod, and the write of the status is allowed, the message of the condition `Ready` ends with `refused by the API server:` and the name of each refused call with the reason that the API server gave; the reason of the condition does not change, and the text goes when the call is allowed again, the pod is gone or the call is no longer due. When the write of the status is refused too, nothing is written. A resource in a namespace where the keeper has no right is not reported. The keeper calls only the API server and the store. The client of the store and the client of the API server use the verifier of the system (`rustls-platform-verifier`, which reads the system root certificates), and the dependency tree has no `webpki-roots`. In a pod the configuration of the API client holds the CA certificate that the service account mounts, and `kube` verifies the API server with that certificate alone; it falls back to the system roots only when the configuration holds none. That behaviour of `kube` is the documented behaviour of the dependency, and no test of this crate checks it: the lock file proves only which TLS crates are in the dependency tree, and no test refuses a bad certificate in a handshake.

## What the keeper connects to

The keeper opens no connection to a sandbox, and no process of the keeper runs in a sandbox namespace. It calls only the Kubernetes API server and the store: no other service, no vendor, no telemetry, no licence endpoint.

The proof is the dependency gate, the configuration type and the rights table. No test observes the network of a running keeper. A cluster can enforce the sentence with an egress policy on the namespace of the keeper.

| Proof | What it holds |
|---|---|
| Dependency gate (`tests/dependency_gate`) | A test reads `cargo metadata --locked` (the packages of every target platform; a cold package cache needs the network once) for the normal (non-dev) dependency tree of this crate only; no other crate of the repository is checked. It fails when a crate of a network class enters the tree and is not in the allowed list. The seven classes are data in the test: HTTP clients and transports, Kubernetes clients, object store clients, gRPC clients, telemetry and error reporting exporters, vendor SDKs, and update, licence or other network protocol clients (message buses, databases, mail, DNS, SSH). The allowed list is eleven crates: `kube` and `kube-client`, `object_store` and `reqwest`, and the transport they need (`hyper`, `hyper-util`, `hyper-rustls`, `hyper-timeout`, `h2`, `tungstenite`, `tokio-tungstenite`). The direct dependencies are a closed list: adding or removing one fails the test until the list is changed on purpose. Tests of the checking code with a fake tree that holds a banned crate (fails) and a clean tree (passes) prove that the gate bites, and a test of the reader proves that dev and build edges are not followed. Limits: a client crate that is in no class and enters below a direct dependency is not seen; the closed list sees only a new direct dependency, not a crate that enters below one (new version, new feature); the gate checks which client libraries are in the tree, not which host an allowed client (`reqwest`, `hyper`, `kube`) calls. The configuration type (a heuristic over key names) and the egress policy of the cluster bound that. |
| Configuration type | The only key that names a remote endpoint is `store_endpoint`; `listen_address` is the address that the health endpoint binds. A key that the type does not know (`otlp_endpoint`, `sentry_dsn`, `proxy_url`, `update_url`, `kube_api_url` and so on) is a start fault. |
| Rights table | The table has no right on `pods/exec`, `pods/attach`, `pods/portforward` or `pods/proxy`, none on `nodes/proxy` or `services/proxy`, and no `create` on `pods`. The keeper has no way to open a stream to a pod through the API server, and it cannot start a process in a namespace of a sandbox. |
| Pod template | The keeper changes the image and the resources of the agent container and the template hash annotation, and nothing else of the template that the ConfigMap gives (a test on the builder of the template). |

The network control of the cluster for "no connection other than the API server and the store" is the egress policy of the chart 0.4.0 (`br-sandbox-egress-keeper`, with `br-sandbox-default-deny`, in the system namespace). Limits: it is not tested on a cluster yet, and the kubelet probes under a default-deny policy depend on the network plugin. The dependency gate stays required.

## Not guaranteed

- `v1alpha1` can change with no conversion and with no promise.
- The fence check proves the names, the shape of the default-deny policy and that no other network policy is there. It does not prove the content of the other fence objects: a person who can write these objects in the namespace can make a fence that passes the check and protects nothing. The labels of a namespace are written by the one who declares it, so a label is an input of the keeper and not a proof of the choice of the platform.
- The removal of a pool has three limits: a claimed pod runs on in a namespace that lost its fence until its turn ends or an expiry rule removes it; a short loss of a fence object empties the warm pool; if the one binding of the admission policy goes, every managed namespace is not fenced and every pool is removed until the binding is back.
- The keeper adds no cap on `maxReplicas`; the quota of the namespace is the only bound above it.
- A larger `disk` does not raise the `sizeLimit` of the `emptyDir` volumes.
- The admission policy of the chart judges a new pod against every resource of the namespace, so a second resource with another image or a smaller size stops the new pods of the namespace until it is removed.
- The proof of the owner reference was made with the admission plugin that checks the right on finalizers not enabled, and the check was not run with that plugin on.
- A warm pod of an old template stays until a rollout step reaches it, at most `warm_max_age_seconds`, except a Pending pod that the scheduler marks Unschedulable, which is held. A rollout stops while the pods of the current template fail.
- A namespace that loses the managed label is dropped when the watch of the namespaces tells it: its pods are forgotten, the keeper deletes no ReplicaSet there and no pod expires there until the label is back. A namespace that gets the label is served as soon as the watch tells it.
- The check that the definition of the resource is present runs through the list of the resources of a managed namespace; with no managed namespace there is no list, and the keeper cannot say the definition is absent.
- A pool whose resource view breaks after the first sync gets no new status until the view is synced again.
- The `desiredReplicas` of a resource whose spec is invalid is the replicas of its ReplicaSet (0 when it has none), not a size that the sizing rule gave.
- A resource in a namespace where the keeper has no right is not reported.
- "Has not yet been Ready" is what a replica saw on its own watch. No field of a pod object says that the pod was Ready once, and the keeper does not guess it from timestamps. After a restart of a replica, a warm pod that was Ready earlier and is now not Ready with a container in `CrashLoopBackOff` is judged as never Ready: the pool goes `True` with the reason `StartCrashing` until that pod becomes Ready, is deleted at `warm_max_age_seconds`, or is seen Ready by the replica.
- The events `PoolAtMax` and `WarmPodsPending` are raised once for each transition or pod in the memory of a replica: a new leader or a restart may raise one again.
- A pool is judged only after the first full sync of its namespace (its pods, its resources, the namespaces and the binding); until then its replicas, its condition and its status stay as written.
- With no keeper running no save is deleted and no pool is resized.
- In the virtual-host style of the store (`store_path_style` false, the default), the keeper and the adapter `br-runner-sandbox` build the object URL with a double slash before the key. This is a known defect. The keeper does not promise a fix; a fix, when it comes, goes out in both crates together and never in one alone. Use `store_path_style` true.
- The keeper applies `spec.replicas` (field manager `br-sandbox-keeper`), `spec.template` (field manager `br-sandbox-keeper-template`) and the condition `WarmPodsFailing` (field manager `br-sandbox-keeper`, status subresource) by server-side apply with `force`. A field that another field manager holds is taken over with no conflict, no log and no event. A chart that renders `spec.replicas` is overwritten by the keeper, and nothing reports it.
- The rule of server-side apply that the tests use (what each field manager owns after a create and after an apply, and what a later apply removes) is a model of the documented semantics, kept in the fake API server of the tests. The fix of the replicas apply and the upgrade write (including the one write of each pool at its first evaluation) were not observed on a real API server in this version. The fix rests on the API server recording the entry of the template manager when an apply changes no value for a field (co-ownership of an equal value). If the server did not record it, the keeper would write the whole template at each evaluation of the pool (one write per pass, no other effect), and the fix would not hold for a ReplicaSet whose fields were never changed. This was not observed on a real API server in this version.
- No test observes the network of a running keeper; the sentence "no connection other than to the API server and the store" (no other service, no vendor, no telemetry, no licence endpoint) rests on the dependency gate, the configuration type and the rights table, with the limits stated in "What the keeper connects to". The rights test fixes the calls to the API server, and a CI gate checks that the crate has no bus access. The code holds no other client. The dependency gate fails when a crate of a network class enters the dependency tree of this crate outside its allowed list, but it does not see a client crate that is in no class and enters below a direct dependency, and it does not see the host that an allowed client (`kube`, `object_store`, `reqwest`) calls; no test observes that.
- A crash between the delete of the manifest and the delete of a part leaves that part to the orphan rule, because the next sweep finds no manifest. The part goes at the first sweep after its newest object is older than `attempt_ttl_seconds`, and not at the next sweep when it is younger than that. A part is written at or before `made_at`, so when `save_ttl_seconds` is above `attempt_ttl_seconds` (3600 by default) the part is already older than `attempt_ttl_seconds` once the save is expired, and the next sweep removes it. When `attempt_ttl_seconds` is the larger of the two, the part stays until it is that old.
- The manifest of every listed save, and every listed record and tombstone, is read on every sweep, and its age comes only from its content.
- The pool size follows the claim rate with the lag of one bucket (`rate_bucket_seconds`) for a change that is not caused by a pod or resource event, because the controller evaluates every pool at each bucket. A change of the template ConfigMap is seen within one bucket for the same reason.

## Why

| Thing | Why it is the way it is |
|---|---|
| Each replica counts claims from its own watch | A change of leader loses no rate; a cold start gives the floor |
| The tombstone has no skew margin | The adapter's read-side check fires first; the tombstone is the same bytes whenever it is written, so no conditional write is needed |
| The tombstone is written before the manifest is deleted | The adapter never meets "record done, no manifest, no tombstone" for a save that the keeper expired |
| The manifest is deleted before the parts | No half of a save is ever visible |
| `GuardedBucket` wraps the store client | The rule "writes only under `tombstones/`" is enforced by one type, not by the care of each call |
| A failed action counts in `sweep_errors_total` | The metrics list has no other error counter; the action is tried again at the next event or pass |
| `/readyz` reflects only the start checks and the first sync | A lost API or store at run time is logged and counted; the replica stays up and tries again |
| The time zone database is embedded (`jiff` with `tzdb-bundle-always`) | The image has no zoneinfo files; the zone of the floors of the day must resolve by name with no file |
| `reqwest` is declared and no line names it (`cargo-machete` ignores it) | It fixes the TLS features of the HTTP client of `object_store`: rustls with the system roots and no bundled provider. The crate installs `ring` itself, and the tree has no `webpki-roots` |
| A pool is judged only after the first sync of its namespace | A new leader that judged the pool before it had seen the pods would write `False` over a `True` of the previous leader |
| The keeper remembers that a pod was Ready | The pod object says only whether it is Ready now; a pod that crashes after it served is not an image failure. The memory is lost at a restart (see "Not guaranteed") |
| Every record and tombstone is read on every sweep | The rule for a record and a tombstone counts the age from the end time, the start time or `expired_at`, which only the content holds. A tombstone is written at the sweep, which can be much later than `expired_at` after a long stop, so the store time can only delay a delete |
| The document of the chart is proved by the real type, up to the chart 0.4 | The chart in this tree is 0.3.0 and renders `pools`, which the keeper 0.2 refuses at start; the chart that works with this keeper is the chart 0.4.0, released after it. `tests/chart_config.rs` renders `charts/br-sandbox-chart` with `helm template` for each values file of the chart CI that enables the keeper and checks that the keeper refuses that document with the fault for `pools`; it loads the committed file `tests/fixtures/chart-0.4-keeper-document.json`, written from the configuration table of this README (no `pools`, `agent_container` set, the keeper-wide keys), through `KeeperConfig::from_json`. That file is not a render of a chart: no test here proves that the chart 0.4.0 renders it. `tests/chart_values.rs` renders `ci/keeper-nondefault-values.yaml`, which sets each mapped value away from its default, and loads the keeper-wide keys of that document, with `pools` removed and `agent_container` set, through `KeeperConfig::from_json` to compare them with the values. The tests that render the chart with `helm template` need `helm` and fail without it; the two tests of `tests/chart_config.rs` that read the fixture only, and the test of `tests/chart_values.rs` that reads the values file only, do not |
| The logs are proved by running the binary | `tests/binary.rs` starts the real binary with no configuration and parses every line it writes as a JSON object |
| The TLS roots are proved by the lock tree | `kube-client` and `reqwest` (the client of the store) each depend on `rustls-platform-verifier`, and no `webpki-roots` is in the tree; a handshake test would need a private key in the repository |

## Pure rules of the pool resource (`pool`)

The module `pool` holds the rules of a `SandboxPool` as pure functions of facts and of an instant given by the caller. The functions do no I/O; the controller reads the resource, the ConfigMap and the network policies through the cluster I/O layer and calls them.

| Part | What it does |
|---|---|
| `validate` | `validate_spec` and `validate` give `InvalidSpec { field, reason }`: image not blank, quantities above zero and request not above limit (compared exactly, to one billionth), `minReplicas` not above `maxReplicas`, at most 16 windows, time texts of at most 64 characters, a window that ends after it begins. |
| `template` | `PoolTemplate::read` checks the ConfigMap `br-sandbox-pod-template`, key `pod-template.json`, and gives `TemplateFault::Absent` or `Invalid`; `render` changes only the image, the resources of the agent container and the annotation `{label_prefix}/template-hash` (SHA-256 of the canonical JSON taken before the annotation is set). |
| `fence` | `fence_verdict` names the object that fails: namespace labels, quota `br-sandbox-quota`, the default-deny policy and its shape, a network policy outside the closed list, the binding `br-sandbox-pod`. It reads no Role. |
| `duplicate` | `pool_winner` and `is_duplicate`: the older resource keeps the pool, then the smaller name; a missing creation time loses. `replicaset_name` gives `warm-{namespace}`. |
| `status` | `judge_acceptance` (order: not observed, not fenced, duplicate, invalid spec, template), `compute_status` (conditions `Accepted`, `Ready`, `WarmPodsFailing`; `lastTransitionTime` moves only when a status changes; `observedGeneration` is kept when not observed) and `decide_write` (no write when the values are equal, at most one write every 5 seconds). |
| `selector` | the label selector text and the `LabelSelector` object, with an error for an operator that is unknown. |

`rules::plan_rollout` plans the rolling replacement from the pods, the current hash, `scale_down_step` and the ReplicaSet replicas: pods that are not Ready go first, then the oldest; it stops while a pod of the current template fails, waits while a current pod is not Ready or a replacement is missing, and never picks a claimed pod or a pod that is being deleted. A warm pod with no hash, or one that cannot be read, is never stale and is listed as unreadable. `judge_pod` takes a flag for a pod chosen by the rollout (delete reason `Rollout`), and a warm pod that is Pending with `PodScheduled` false and the reason `Unschedulable` has no age deadline and, when it is not failing, still gets the alarm.

## Why (reconcile)

| Thing | Why it is the way it is |
|---|---|
| A pod expires by the same rules in a namespace with no resource | The keeper acts on every pod with the pool-state label; a pod must not stay for want of a resource |
| A pool is judged at each rate bucket as well as on events | The floor of the day, the sliding window and the template ConfigMap change the result with no event that the keeper holds |
| The pool of a resource is the namespace | The adapter finds the ReplicaSet `warm-{namespace}`; the pool id of a pod is the name of its namespace |
| `/readyz` flips on an absent definition and not on a later broken watch | A missing definition means that no pool can be served and a person must act; a watch that breaks is repaired by the next list |
| The condition and the status share one function | The two conditions cannot differ |
| The status is not written before the first full sync of the namespace | A status that says `NotObserved` at the start is noise, and the 5-second bound would delay the true status |
| An invalid spec shows the replicas of its ReplicaSet in `desiredReplicas` | The sizing rule is not run for a spec that failed its rules |
