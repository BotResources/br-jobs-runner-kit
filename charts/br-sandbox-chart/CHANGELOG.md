# Changelog

## 0.2.0

The egress proxy. A (client, mode) that uses a proxy (mode `allow`, and mode `full` with a credential set) renders the proxy when `egress.enabled` is true.

Upgrade from 0.1.0: an install with `egress.enabled: true` now fails the render until `egress.proxy.reload.key_secret`, `clients.<client>.modes.<mode>.proxy.cluster_ip` and `clients.<client>.modes.<mode>.proxy.ca.certificate` (and `proxy.ca.key_secret`) are set; the render errors name each missing key (`BR_SANDBOX_MISSING_VALUE`). `credential_set` is now validated by the schema and the render (it took any key before): an item outside the documented keys, an empty `hosts` and the other errors below fail the render. `secret_ref` and `secrets` must be given together and `secrets` needs at least one item: a 0.1.0 value with only one of them, or with an empty `secrets`, now fails.

- In each egress namespace: ConfigMaps `br-sandbox-proxy-config` and `br-sandbox-proxy-ca`, Deployment `br-sandbox-proxy` (label `br.sandbox/role=proxy`) and Service `br-sandbox-proxy` with a fixed `clusterIP` (`proxy.cluster_ip`) on `egress.proxy.port`. The pod has no ServiceAccount token, `hostUsers: false`, a numeric non-root user, `drop ALL`, a read-only root file system, seccomp `RuntimeDefault`, `dnsPolicy: None` with `network.public_resolvers`, and resource requests and limits from `egress.proxy.resources`. No Role and no RoleBinding exist in an egress namespace. The chart renders no Secret.
- The proxy image is `egress.proxy.image.{repository,digest}`, by digest only (a tag fails the schema), with the `registry_mirror` prefix and the `pull_secrets`.
- The proxy config is standalone: no control-plane token, no tenancy block, no telemetry endpoint, no response-retry handler, no DNS server. Tunnel listener on `egress.proxy.port`; the other listeners bind the loopback address of the pod; TLS mode `mitm` with the CA certificate from a ConfigMap and the CA key from the Secret named by `proxy.ca.key_secret`. Transforms in fixed order: `allowlist` (mode `allow`: `allow.domains` and `allow.cidrs`; mode `full` with a credential set: the pattern `*`), then `secrets`. `upstream_deny_cidrs` is the deny list of the `egress-proxy` policy plus the loopback ranges. There is no response scrub.
- Credential set (mode `allow` or `full`; `credential_set.{secret_ref,secrets}`): per item `placeholder`, `env_name`, `key`, `hosts`, `match_headers`, `match_query`, `match_path`, `match_body`, `require_tls` (default true), `require` (default false). The real values are files of the Secret `secret_ref`, mounted in the proxy pod only. New render errors: `BR_SANDBOX_CREDENTIAL_HOSTS_EMPTY`, `BR_SANDBOX_CREDENTIAL_PLACEHOLDER_EMPTY`, `BR_SANDBOX_CREDENTIAL_PLACEHOLDER_DUPLICATE`, `BR_SANDBOX_CREDENTIAL_ENV_DUPLICATE`, `BR_SANDBOX_CREDENTIAL_ENV_RESERVED` (an `env_name` that the chart sets itself), `BR_SANDBOX_CREDENTIAL_HOST_WILDCARD` (`*` or a `/0` CIDR as a bound host), `BR_SANDBOX_CREDENTIAL_KEY_DUPLICATE`, `BR_SANDBOX_CREDENTIAL_REQUIRE_TLS`, `BR_SANDBOX_PROXY_ADDRESS_DUPLICATE`, `BR_SANDBOX_PROXY_PORT_CONFLICT`, `BR_SANDBOX_PROXY_QUOTA`. `credential_set` is now strict in the schema. In mode `allow` the `secrets` transform comes after the allowlist, so a bound host must be on the allow list too. A bound host that sends the real value back shows it to the sandbox: there is no response scrub. `BR_SANDBOX_EGRESS_DISABLED` stays for `egress.enabled: false`.
- Sandbox side, through the egress slots: `HTTPS_PROXY`, `HTTP_PROXY` (and lower case) set to the Service address, `NO_PROXY` empty, the placeholders as variables, the CA ConfigMap `br-sandbox-ca` in the sandbox namespace mounted read-only, and the variables of `egress.ca.env_names` pointing to it. No Secret volume and no `secretKeyRef` in a sandbox pod. The slots now receive `dict "root" . "ns" $ns`.
- Network check: the CONNECT probe has no positive control in the Job (a proxy that refuses everything passes the off-list check); a cluster test is to check that a listed host is reached. The pod targets leave out the pods labelled `br.sandbox/role=proxy`. In mode `allow` the probe pod of a (client, mode) with a proxy sends `CONNECT` through the proxy to each target and to `network_check.offlist_host`, and reads the status line of the answer to the `CONNECT`: `refused` for 403 or 502, `reached` for 200, `no_result` for any other answer or none (the Job fails on any verdict other than `refused`). The status code is the second field of the status line, compared as a whole field (`HTTP/1.1 200 x 403 y` is read as 200); a status line with no three-digit code is `no_result`. Captured on the pinned proxy image (0.61.0), mode `allow`: an IP address that is not on the list and an internal IP address both got 403 at the `CONNECT`; a name that is not on the list was not captured at the `CONNECT`. The Job does not probe the path through the proxy in mode `full`: captured on the pinned proxy image (0.61.0) with a credential set, in containers on a network with no route out, the proxy answered 200 to every `CONNECT` and refused only at the first request inside the tunnel, with a 502 that a reached target which does not speak HTTP also gave, so a probe from the sandbox side cannot give an exact verdict. On a deployed cluster the Job therefore does not prove the pivot barriers of mode `full`; that proof, a test server at an internal address that records its connections and sees none after a request through the proxy, is to be made on a test cluster; no such test exists in this repository at this version and none was executed. What the Job proves is the direct TCP probes of the sandbox pod, in the three modes, and the refusal at the `CONNECT` in mode `allow`. In mode `allow` the Job sends each `CONNECT` once, with all barriers in place: a 403 can come from the allowlist alone, before the deny list or the network policy acts, so the Job does not show that the deny list or the policy would refuse the target if the allowlist were absent. That test (each barrier alone), which renders the chart with only one barrier and runs the check against it, is to be made on a test cluster; no such test exists in this repository at this version and none was executed. The JSON line carries `kind` `tcp`, `connect`, `target_class` or `node_list`: `tcp` carries `observed` `refused`, `reached` or `no_result` and `control` `ok` or `control_unavailable`; `connect` carries `observed` `refused`, `reached` or `no_result` and `control` `not_applicable`; `target_class` carries `observed` `missing` and `control` `ok`; `node_list` carries `observed` `stale` and `control` `ok`. The `expected` word of a connect line is `refused`. The check image needs `awk` besides the tools of 0.1.0, and an `nc` that reads the reply until the proxy closes; no real `nc` build was executed at this version, and the README says what the first cluster test must confirm.
- Config changes roll the pods: the pod template carries `br.sandbox/proxy-config-sha256` and `br.sandbox/proxy-ca-sha256`, the SHA-256 of the rendered proxy config and of the CA certificate. A change of the content of a Secret or of a ConfigMap that the chart does not render does not roll the pods; the project restarts them or calls the reload API itself.
- The reload and metrics listeners are constants on the loopback address (`127.0.0.1:9092`, `127.0.0.1:9090`); there is no key `egress.proxy.reload.listen`. The reload API is enabled and reachable only inside the proxy pod; nothing in the chart calls it.
- `proxy.ca.certificate` takes `CERTIFICATE` blocks only: a PEM block of another type (a private key) fails the schema. `proxy.cluster_ip` is an IPv4 address; an IPv6 value fails the schema.
- Optional `egress.proxy.upstream_ca.{config_map,key}` (`key` defaults to `ca.crt`): the proxy trusts the system roots of its image; when set, the chart mounts that key of a ConfigMap of the egress namespace (that the project creates) read-only at `/etc/iron-proxy/trust/` and sets `SSL_CERT_FILE` on the proxy container to the file. Measured on the pinned proxy image (0.61.0, arm64 only, in a container on a network with no route out): the roots of the file are added to the roots of the certificate directory of the image; they do not replace them, so the public roots stay trusted and the file alone is enough to trust a private authority. Nothing was measured about the default bundle file of the image when `SSL_CERT_FILE` is set. Unset renders nothing.
- Targets: `allow.cidrs` allows the `CONNECT` to an address and the render needs no name for it, but TLS to an IP literal does not work on the pinned proxy image (0.61.0), measured on the arm64 image only (the proxy needs a server name in the TLS handshake and clients send none for an IP): use a name. A name target works end to end on that image; a private test server needs a DNS that answers its names and a certificate authority that the proxy trusts (`egress.proxy.upstream_ca`).
- New keys: `egress.proxy.{image,replicas,resources,reload.key_secret,upstream_ca}`, `egress.ca.env_names`, `network_check.offlist_host`, `clients.<client>.modes.<mode>.proxy.{cluster_ip,ca}`.
- Constants, not keys: the numeric user and group of the proxy pod (65532, also its `fsGroup`) and the mount path of the CA certificate in the sandbox (`/etc/br-sandbox-ca`). The Deployment sets `maxSurge: 1` and `maxUnavailable: 0`, so the surge is one pod whatever the replica count and `BR_SANDBOX_PROXY_QUOTA` counts it right: with a pod quota of 4, 3 replicas render and 4 replicas fail; with a pod quota of 5, 4 replicas render.
- The CA reaches the tools of the sandbox only through the mounted file and the variables of `egress.ca.env_names`; the system bundle of the sandbox image is not changed, so a tool that ignores those variables refuses the proxy certificate.
- Limits of the measurements: only the arm64 image of the pinned digest was started, all captures were taken in containers on a network with no route out, not in a cluster, and the amd64 image was not started. The chart relies on an assumption that it does not test: that a proxy with no token set makes no call to its vendor, while the `egress-proxy` policy lets the proxy reach public addresses; a ten-minute idle capture of the pinned proxy image (0.61.0) on an isolated network showed 0 IPv4 packets (IPv6 frames were counted and not decoded; the ten minutes were taken with the config of mode `full` only), which does not cover a call after a rare event or on another version, and a new digest needs a new capture. That each placeholder is bound to its `hosts`, that `require_tls` keeps a bound value off plain HTTP and that `require` makes the proxy answer 403 to a bound host that sends no placeholder are the documented behaviour of the proxy product, not measured here; the intended path for git is HTTPS with the token as placeholder, and the form measured on the pinned proxy image (0.61.0) is a plain HTTPS GET with a Bearer header (no git client was used). The admission policy refusing a Secret volume, `secretKeyRef` and `secretRef` is stated with the policy expressions not executed.
- The fixture `ci/egress-values.yaml` holds a complete proxy set-up for the offline suite.

## 0.1.1

Fixes and a new render failure.

- New render failure `BR_SANDBOX_RUNNER_IS_POD_IDENTITY{client,mode,namespace}`: a `runner.service_account` named `sandbox` with a `runner.namespace` that is a sandbox namespace of the installation fails the render. The runner identity must not be the identity of the sandbox pods. Values that passed before with such a pair now fail; any other pair is unchanged.
- New rule `BR_SANDBOX_RUN_AS_NON_ROOT` in the admission policy: every container of a `role=sandbox` pod (`containers`, `initContainers` and `ephemeralContainers`) sets `runAsNonRoot: true` and a `runAsUser` above 0 in its own `securityContext`, and the pod does not share its process namespace. The policy has thirteen rules now. Two exceptions: the seed container of the regular `containers` list, by its name and by its exact tools image (with the mirror prefix), still pinned to root, a read-only root file system and no port (an init container or an ephemeral container with the seed name and the tools image is held to the plain non-root condition and is refused as root); and the pods of the network check, which run as uid 0, by the user name `system:serviceaccount:{system namespace}:br-sandbox-netcheck` (no exception when `network_check.enabled` is false). The policy also watches `UPDATE` of `pods/ephemeralcontainers`.
- Upgrade effect: the new rule runs on every `UPDATE` of a `role=sandbox` pod. The agent container of any pod of a sandbox namespace made by chart 0.1.0, warm or claimed, has no `runAsNonRoot`, so after the upgrade the next `UPDATE` of that pod is refused until the pod is recreated: the claim patch for a warm pod, a later label or annotation update for a claimed pod. A ReplicaSet does not recreate running pods when its template changes, and a claimed pod is not owned by the ReplicaSet. Before the claim path is used, delete the old warm pods of every sandbox namespace; the ReplicaSet recreates them from the new template. For a claimed pod, let the agent finish and delete the pod, or delete it at once.
- Rule `BR_SANDBOX_RUN_AS_NON_ROOT` is the only rule that reads `ephemeralContainers`; the container rules 4 to 7 read `containers` and `initContainers`, rule 9 reads `containers`. No Role of the chart holds a verb on `pods/ephemeralcontainers`.
- The agent container and the init container of the pod template set `runAsNonRoot: true`. A render with `runAsUser` or `runAsGroup` 0 still fails (schema minimum 1).
- The README lists the rule and states that no rule protects the seed against a compromised adapter.
- The README states that a node needs a kubelet with subordinate id ranges for user namespaces, that the chart ships and requires no node label for it, that a node without it refuses the pod at start (kubelet behaviour, proved on a cluster only, not yet executed), and that `pool.node_selector` restricts the pool to prepared nodes.
- The README states that the check of foreign values in the chart files covers registries and host names only, and that a client or project name is checked by review.
- Tests: the size of the pool is checked against the values of the LimitRange (default request, default, max), the six quantities of the ResourceQuota and the six bounds of the size rule of the admission policy, with two sizes. No binding of the render names the `sandbox` service account of a sandbox namespace. `pool.node_selector` reaches the pod. The check of foreign values no longer reads a variable that nothing sets.

## 0.1.0

First release. The chart of the sandbox: one installation per cluster, one namespace per (client, mode).

- Per (client, mode): Namespace (Pod Security `baseline` enforced, `restricted` warn and audit), ResourceQuota (size times `max_sandboxes` + `quota.extra_pods`, plus the resources of the seed container of each sandbox when it is enabled), LimitRange, ServiceAccount `sandbox` without token, the warm pool (ReplicaSet without `spec.replicas`: a value rendered by the chart would be reset at each `helm upgrade`, so the keeper is the only writer of the replica count; a pool starts with one replica until the keeper runs, and `pool.floor` is read by the keeper, not applied by the chart), NetworkPolicies, admission policy and binding, runner Role, ConfigMap `br-sandbox-config`.
- The pod-level seccomp profile is `RuntimeDefault`, and a container that sets its own `seccompProfile` must set `RuntimeDefault` too.
- Modes `none`, `allow`, `full`. `none` has only `default-deny`. `full` opens the public addresses except every internal list. `allow` opens only the pods `br.sandbox/role=proxy` of the egress namespace of the same (client, mode) on the proxy port; namespace and pod are selected in the same rule item. The proxy itself is not rendered yet.
- A (client, mode) that uses a proxy (mode `allow`, and mode `full` with a non-empty `credential_set`) has a second namespace `{sandbox namespace}-egress` for the proxy pods, the credential Secret and the CA key. It carries `br.sandbox/egress=true`, the client and mode labels and the Pod Security labels of the sandbox namespace, and never `br.sandbox/managed`. It holds a default-deny, `ingress-tunnel` (only from the sandbox namespace of the same (client, mode), TCP on `egress.proxy.port`), `egress-proxy` (public addresses except the internal, pod, service, node, node public and load balancer lists) and a ResourceQuota on pods (`egress.quota.pods`, default 4). No identity of the chart has a Role or a RoleBinding there. The name comes from the helper `br-sandbox-chart.egress.namespace`; a name over 63 characters fails with `BR_SANDBOX_NAME_TOO_LONG`.
- Mode `full` with a credential set reaches only the proxy; its pod resolver is `127.0.0.1`. A `credential_set` on mode `none` fails the render with `BR_SANDBOX_CREDENTIAL_SET_MODE`. A runner namespace equal to an egress namespace fails with `BR_SANDBOX_SHARED_NAMESPACE`.
- The admission policy matches every pod of a managed namespace. A pod passes if it is `role=sandbox` and follows rules 1 to 9 and the label rules; any other role is refused, `role=proxy` included.
- The sandbox pod has an init container that copies `bsdtar` and `pause` from `br-sandbox-tools`, and a second root container `seed` (key `tools.seed_container.enabled`) that writes `/skills`, which the agent mounts read-only.
- The network check fails when a class of target has no target (listed targets, node kubelet, node API, API service, DNS service, cluster name, pod IP), with one report line per missing class.
- Once per installation: system Namespace, keeper Deployment, Roles and NetworkPolicies (when `keeper.enabled`), the network check Job and its ClusterRole (when `network_check.enabled`).
- Empty extension points for the egress proxy and the keeper objects: the named templates `br-sandbox-chart.slot.egress.*` and `br-sandbox-chart.slot.keeper.objects`. They render nothing.
- The egress namespaces and their policies render for every mode `allow`, and for mode `full` with a `credential_set`, whatever the value of `egress.enabled`. `egress.enabled: true` lets the `allow` lists and the credential sets pass the validation; it stays `false` until the proxy objects exist, which come with a later change of this chart. The slot `br-sandbox-chart.slot.egress.objects` is called once per egress namespace and receives its name. While `egress.enabled` is false, a non-empty `allow` list or `credential_set` of a mode fails the render with `BR_SANDBOX_EGRESS_DISABLED{client,mode,key}`. While it is true, a non-empty `allow` list in mode `none` or `full` fails with `BR_SANDBOX_ALLOW_MODE{client,mode}`.
- No Secret and no bucket is rendered. No object of the chart says that a response is scrubbed: the proxy has no response scrub.
- Public inputs, documented in the README: `registry_mirror`, `pull_secrets`, `image_pull_policy`, `runtimeClassName`, `runAsUser`, `runAsGroup`, `warm_max_age_seconds`, the per-mode `pool` override, `pool.node_selector`, `keeper.settings`, and the label contract. `values.schema.json` is strict: a key outside its place fails the render.
