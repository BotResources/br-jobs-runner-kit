# Changelog

## 0.2.0

The egress proxy. A (client, mode) that uses a proxy (mode `allow`, and mode `full` with a credential set) gets a working proxy when `egress.enabled` is true.

- In each egress namespace: ConfigMaps `br-sandbox-proxy-config` and `br-sandbox-proxy-ca`, Deployment `br-sandbox-proxy` (label `br.sandbox/role=proxy`) and Service `br-sandbox-proxy` with a fixed `clusterIP` (`proxy.cluster_ip`) on `egress.proxy.port`. The pod has no ServiceAccount token, `hostUsers: false`, a numeric non-root user, `drop ALL`, a read-only root file system, seccomp `RuntimeDefault`, `dnsPolicy: None` with `network.public_resolvers`, and resource requests and limits from `egress.proxy.resources`. No Role and no RoleBinding exist in an egress namespace. The chart renders no Secret.
- The proxy image is `egress.proxy.image.{repository,digest}`, by digest only (a tag fails the schema), with the `registry_mirror` prefix and the `pull_secrets`.
- The proxy config is standalone: no control-plane token, no tenancy block, no telemetry endpoint, no response-retry handler, no DNS server. Tunnel listener on `egress.proxy.port`; the other listeners bind the loopback address of the pod; TLS mode `mitm` with the CA certificate from a ConfigMap and the CA key from the Secret named by `proxy.ca.key_secret`. Transforms in fixed order: `allowlist` (mode `allow`: `allow.domains` and `allow.cidrs`; mode `full` with a credential set: the pattern `*`), then `secrets`. `upstream_deny_cidrs` is the deny list of the `egress-proxy` policy plus the loopback ranges. There is no response scrub.
- Credential set (mode `allow` or `full`; `credential_set.{secret_ref,secrets}`): per item `placeholder`, `env_name`, `key`, `hosts`, `match_headers`, `match_query`, `match_path`, `match_body`, `require_tls` (default true), `require` (default false). The real values are files of the Secret `secret_ref`, mounted in the proxy pod only. New render errors: `BR_SANDBOX_CREDENTIAL_HOSTS_EMPTY`, `BR_SANDBOX_CREDENTIAL_PLACEHOLDER_EMPTY`, `BR_SANDBOX_CREDENTIAL_PLACEHOLDER_DUPLICATE`, `BR_SANDBOX_CREDENTIAL_ENV_DUPLICATE`, `BR_SANDBOX_CREDENTIAL_ENV_RESERVED` (an `env_name` that the chart sets itself), `BR_SANDBOX_CREDENTIAL_HOST_WILDCARD` (`*` or a `/0` CIDR as a bound host), `BR_SANDBOX_CREDENTIAL_KEY_DUPLICATE`, `BR_SANDBOX_CREDENTIAL_REQUIRE_TLS`, `BR_SANDBOX_PROXY_ADDRESS_DUPLICATE`, `BR_SANDBOX_PROXY_PORT_CONFLICT`, `BR_SANDBOX_PROXY_QUOTA`. `credential_set` is now strict in the schema. In mode `allow` the `secrets` transform comes after the allowlist, so a bound host must be on the allow list too. A bound host that sends the real value back shows it to the sandbox: there is no response scrub. `BR_SANDBOX_EGRESS_DISABLED` stays for `egress.enabled: false`.
- Sandbox side, through the egress slots: `HTTPS_PROXY`, `HTTP_PROXY` (and lower case) set to the Service address, `NO_PROXY` empty, the placeholders as variables, the CA ConfigMap `br-sandbox-ca` in the sandbox namespace mounted read-only, and the variables of `egress.ca.env_names` pointing to it. No Secret volume and no `secretKeyRef` in a sandbox pod. The slots now receive `dict "root" . "ns" $ns`.
- Network check: the CONNECT probe has no positive control (a proxy that refuses everything passes the off-list check); the cluster tests check that a listed host is reached. The pod targets leave out the pods labelled `br.sandbox/role=proxy`; the probe pod of a (client, mode) with a proxy sends `CONNECT` through the proxy to each target and, in mode `allow`, to `network_check.offlist_host`; the Job fails unless every answer is 403 or 502.
- Config changes roll the pods: the pod template carries `br.sandbox/proxy-config-sha256` and `br.sandbox/proxy-ca-sha256`, the SHA-256 of the rendered proxy config and of the CA certificate. A change of the content of a Secret or of a ConfigMap that the chart does not render does not roll the pods; the project restarts them or calls the reload API itself.
- The reload and metrics listeners are constants on the loopback address (`127.0.0.1:9092`, `127.0.0.1:9090`); there is no key `egress.proxy.reload.listen`. The reload API is enabled and reachable only inside the proxy pod; nothing in the chart calls it.
- `proxy.ca.certificate` takes `CERTIFICATE` blocks only: a PEM block of another type (a private key) fails the schema. `proxy.cluster_ip` is an IPv4 address; an IPv6 value fails the schema.
- Optional `egress.proxy.upstream_ca.{config_map,key}` (`key` defaults to `ca.crt`): the proxy trusts the system roots of its image; when set, the chart mounts that key of a ConfigMap of the egress namespace (that the project creates) read-only at `/etc/iron-proxy/trust/` and sets `SSL_CERT_FILE` on the proxy container to the file. Unset renders nothing.
- Targets: `allow.cidrs` allows the `CONNECT` to an address and the render needs no name for it, but TLS to an IP literal does not work on the pinned proxy image (the proxy needs a server name in the TLS handshake and clients send none for an IP): use a name. A name target works end to end on that image; a private test server needs a DNS that answers its names and a certificate authority that the proxy trusts (`egress.proxy.upstream_ca`).
- New keys: `egress.proxy.{image,replicas,runAsUser,runAsGroup,resources,reload.key_secret,upstream_ca}`, `egress.ca.{mount_path,env_names}`, `network_check.offlist_host`, `clients.<client>.modes.<mode>.proxy.{cluster_ip,ca}`.
- The fixture `ci/egress-values.yaml` holds a complete proxy set-up for the offline suite.

## 0.1.0

First release. The chart of the sandbox: one installation per cluster, one namespace per (client, mode).

- Per (client, mode): Namespace (Pod Security `baseline` enforced, `restricted` warn and audit), ResourceQuota (size times `max_sandboxes` + `quota.extra_pods`, plus the resources of the seed container of each sandbox when it is enabled), LimitRange, ServiceAccount `sandbox` without token, the warm pool (ReplicaSet without `spec.replicas`: a value rendered by the chart would be reset at each `helm upgrade`, so the keeper is the only writer of the replica count; a pool starts with one replica until the keeper runs, and `pool.floor` is read by the keeper, not applied by the chart), NetworkPolicies, admission policy and binding, runner Role, ConfigMap `br-sandbox-config`.
- The pod-level seccomp profile is `RuntimeDefault`, and a container that sets its own `seccompProfile` must set `RuntimeDefault` too.
- Modes `none`, `allow`, `full`. `none` has only `default-deny`. `full` opens the public addresses except every internal list. `allow` opens only the pods `br.sandbox/role=proxy` of the egress namespace of the same (client, mode) on the proxy port; namespace and pod are selected in the same rule item. The proxy itself is not rendered yet.
- A (client, mode) that uses a proxy (mode `allow`, and mode `full` with a non-empty `credential_set`) has a second namespace `{sandbox namespace}-egress` for the proxy pods, the credential Secret and the CA key. It carries `br.sandbox/egress=true`, the client and mode labels and the Pod Security labels of the sandbox namespace, and never `br.sandbox/managed`. It holds a default-deny, `ingress-tunnel` (only from the sandbox namespace of the same (client, mode), TCP on `egress.proxy.port`), `egress-proxy` (public addresses except the internal, pod, service, node, node public and load balancer lists) and a ResourceQuota on pods (`egress.quota.pods`, default 4). No identity of the chart has a Role or a RoleBinding there. The name comes from the helper `br-sandbox-chart.egress.namespace`; a name over 63 characters fails with `BR_SANDBOX_NAME_TOO_LONG`.
- Mode `full` with a credential set reaches only the proxy; its pod resolver is `127.0.0.1`. A `credential_set` on mode `none` fails the render with `BR_SANDBOX_CREDENTIAL_SET_MODE`. A runner namespace equal to an egress namespace fails with `BR_SANDBOX_SHARED_NAMESPACE`.
- The admission policy matches every pod of a managed namespace. A pod passes if it is `role=sandbox` and follows rules 1 to 9 and the label rules; any other role is refused, `role=proxy` included.
- The sandbox pod has an init container that copies `bsdtar` and `pause` from `br-sandbox-tools`, and a second root container `seed` (key `tools.seed_container.enabled`) that writes `/skills`, which the agent mounts read-only.
- The network check fails when a class of target has no target (listed targets, node kubelet, node API, API service, DNS service, cluster name, pod IP), with one report line per missing class.
- Once per installation: system Namespace, keeper Deployment, Roles and NetworkPolicies (when `keeper.enabled`), the network check Job and its ClusterRole (when `network_check.enabled`).
- Empty extension points for the egress proxy and the keeper objects: the named templates `br-sandbox-chart.slot.egress.*` and `br-sandbox-chart.slot.keeper.objects`. They render nothing.
- The egress namespaces and their policies render for every mode `allow`, and for mode `full` with a `credential_set`, whatever the value of `egress.enabled`. `egress.enabled: true` lets the `allow` lists and the credential sets pass the validation; it stays `false` until the proxy objects exist, which come with a later change of this chart. The slot `br-sandbox-chart.slot.egress.objects` is called once per egress namespace and receives its name. While `egress.enabled` is false, a non-empty `allow` list or `credential_set` of a mode fails the render with `BR_SANDBOX_EGRESS_DISABLED{client,mode,key}`. While it is true, a non-empty `allow` list in mode `none` or `full` fails with `BR_SANDBOX_ALLOW_MODE{client,mode}`.
- No Secret and no bucket is rendered. No object of the chart says that a response is scrubbed: the proxy has no response scrub.
- Public inputs, documented in the README: `registry_mirror`, `pull_secrets`, `image_pull_policy`, `runtimeClassName`, `runAsUser`, `runAsGroup`, `warm_max_age_seconds`, the per-mode `pool` override, `pool.node_selector`, `keeper.settings`, and the label contract. `values.schema.json` is strict: a key outside its place fails the render.
