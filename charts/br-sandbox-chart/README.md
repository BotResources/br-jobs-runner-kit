# br-sandbox-chart

The Helm chart of the sandbox. One installation per cluster. It renders everything that is declarative: namespaces, quotas, admission policy, network policies, warm pools, roles, the keeper and the network check. Licence: Apache-2.0. The chart is released by the workflow `chart-release`; it is not a library of the Libraries registry.

It does not claim a pod, execute a command, save or restore (the library `br-runner-sandbox`), size a pool or delete a save (the library `br-sandbox-keeper`). It creates no bucket, no Secret and no credential value.

## What a render holds

| Object | Scope | Gate |
|---|---|---|
| Namespace `{prefix}-system` | once per installation | always |
| Namespace `{prefix}-{client}-{mode}`, ServiceAccount `sandbox` (no token, no Role), ResourceQuota `br-sandbox-quota`, LimitRange `br-sandbox-limits`, ConfigMap `br-sandbox-config` (the adapter document, key `config.json`) | each (client, mode) | always |
| ReplicaSet `warm-{client}-{mode}` | each (client, mode) | always; it has no `spec.replicas`, so a pool starts with one replica (the ReplicaSet default) until the keeper runs |
| NetworkPolicy `default-deny`, `egress-full` or `egress-allow` | each (client, mode) | always |
| Namespace `{sandbox namespace}-egress`, NetworkPolicies `default-deny`, `ingress-tunnel` and `egress-proxy`, ResourceQuota `br-sandbox-egress-quota` | each (client, mode) that uses a proxy | mode `allow`; mode `full` when `credential_set` is not empty |
| ConfigMaps `br-sandbox-proxy-config` and `br-sandbox-proxy-ca`, Deployment `br-sandbox-proxy` and Service `br-sandbox-proxy` | each egress namespace | `egress.enabled` |
| ConfigMap `br-sandbox-ca` (the CA certificate, not secret) | the sandbox namespace of each (client, mode) that uses a proxy | `egress.enabled` |
| ValidatingAdmissionPolicy and binding `{prefix}-{client}-{mode}-pod` | each (client, mode) | always |
| Role and RoleBinding `br-sandbox-runner` | each (client, mode) | always |
| Role and RoleBinding `br-sandbox-keeper` | each (client, mode), sandbox namespace | `keeper.enabled` |
| Keeper Deployment, ConfigMap `br-sandbox-keeper-config`, ServiceAccount, lease Role, ClusterRole `namespaces` read, NetworkPolicies `default-deny` and `egress-keeper` | system namespace | `keeper.enabled` |
| ServiceAccount, ClusterRole and Role `br-sandbox-netcheck`, ConfigMap `br-sandbox-netcheck`, Job `br-sandbox-netcheck-{run_id}`, CronJob, NetworkPolicy `egress-netcheck` | system namespace and each (client, mode) | `network_check.enabled` |

The system namespace is `{prefix}-system`. It carries the label `br.sandbox/system=true` and not `br.sandbox/managed`, so the Kyverno exclusion does not touch it.

## Layout: two namespaces for a mode with a proxy

A (client, mode) that uses a proxy has two namespaces. Mode `allow` always has them; mode `full` has them when `clients.<client>.modes.full.credential_set` is not empty. Mode `none` and mode `full` without a credential set have the sandbox namespace only.

| | Sandbox namespace `{prefix}-{client}-{mode}` | Egress namespace `{prefix}-{client}-{mode}-egress` |
|---|---|---|
| Holds | the sandbox pods, the warm pool, the CA certificate (not secret) | the proxy pods, the credential Secret, the CA key Secret, the sealed Secrets of the proxy |
| Label | `br.sandbox/managed=true`, `br.sandbox/mode`, `br.sandbox/client` | `br.sandbox/egress=true`, `br.sandbox/mode`, `br.sandbox/client`; never `br.sandbox/managed` |
| Pod Security | `baseline` enforced, `restricted` warn and audit | the same |
| Role and RoleBinding | `br-sandbox-runner`, `br-sandbox-keeper`, `br-sandbox-netcheck` | none |
| Policies | `default-deny`, `egress-allow` or `egress-full` | `default-deny`, `ingress-tunnel`, `egress-proxy` |
| Quota | `br-sandbox-quota` and `br-sandbox-limits` | `br-sandbox-egress-quota` (pods only, `egress.quota.pods`) |
| Admission policy | one per namespace, `role=sandbox` pods only | none |

No identity of the chart (the runner, the keeper, the network check, the sandbox ServiceAccount) has a Role or a RoleBinding in an egress namespace, so none of them reaches a proxy pod by `pods/exec` or `pods` patch, and none reads a Secret there. The controller of the proxy Deployment is the only identity that makes or changes a pod there. The one cluster-wide right on pods is the read (`get`, `list`) of the network check ClusterRole; no identity has a cluster-wide right on `secrets`. A runner namespace that equals an egress namespace fails the render with `BR_SANDBOX_SHARED_NAMESPACE`.

The egress namespace does not carry `br.sandbox/managed=true`, on purpose: the admission policy of a sandbox namespace binds on that label and refuses every pod that is not `role=sandbox`, so it would refuse the proxy pods. The consequence for a Kyverno exclusion (or any policy that selects the managed namespaces): the exclusion text that names `br.sandbox/managed=true` does not cover the egress namespace. The cluster default network policy (the generated policy per namespace with allow rules for DNS, intra-namespace traffic and ingress controllers) also acts in the egress namespace: without an exclusion that selects `br.sandbox/egress=true`, its allow rules add to `ingress-tunnel` and `egress-proxy`, so the statements above (ingress only from the sandbox pods, no cluster DNS) are not what the cluster enforces there. Any other exclusion the project needs there (user namespaces, runtime class) selects `br.sandbox/egress=true` too. The chart renders no admission policy in the egress namespace, so nothing there requires `hostUsers: false`; the proxy pod sets `hostUsers: false` and the rest of its security context itself. A consumer that lists namespaces by `br.sandbox/client` or `br.sandbox/mode` also sees the egress namespaces and selects `br.sandbox/managed=true` to get the sandbox ones.

**Where the secrets live.** The credential Secret, the CA key Secret and every sealed Secret of the proxy are created in the egress namespace by the deploy tool; the chart renders none. The CA certificate (not secret) stays in the sandbox namespace, for the sandbox pods: the chart renders it there from `clients.<client>.modes.<mode>.proxy.ca.certificate`, and a copy in the egress namespace for the proxy. The Secrets to create in an egress namespace: the one named by `proxy.ca.key_secret` (item `ca.key`), the one named by `credential_set.secret_ref` (one item per `secrets[].key`), and the one named by `egress.proxy.reload.key_secret` (item `token`). The pull secrets of `pull_secrets` must exist in the egress namespace too: an image pull reads the Secret of the namespace of the pod.

**Name.** `{sandbox namespace}-egress` is a working name. It comes from the helper `br-sandbox-chart.egress.namespace`, the only place that writes the suffix; a change of the pattern is a change of that helper. A name over 63 characters fails the render with `BR_SANDBOX_NAME_TOO_LONG`, and a name equal to another namespace of the render (the system namespace, a sandbox namespace, a runner namespace) fails with `BR_SANDBOX_SHARED_NAMESPACE`. One egress namespace belongs to one (client, mode): two clients never share one.

**What the egress namespace renders.** Its Namespace, its default-deny, its two allow rules and its quota; with `egress.enabled` also the proxy objects, through the slot `br-sandbox-chart.slot.egress.objects`, which receives the root, the namespace item and the name of the egress namespace (`dict "root" . "ns" $ns "namespace" $name`). A proxy Deployment lives in an egress namespace and never in a sandbox namespace. With `egress.enabled: false` no proxy pod exists, so a sandbox of a mode with a proxy has no egress at all once the network plugin enforces the policies (fail closed in that steady state, see The enforcement window).

**Rules of the egress namespace.** `default-deny` on every pod, both directions. `ingress-tunnel`: proxy pods take traffic only from the pods `br.sandbox/role=sandbox` of the sandbox namespace of the same (client, mode) (namespace and pod selector in the same item), TCP on `egress.proxy.port`; no other port, so the reload port of the proxy is reached by no sandbox. `egress-proxy`: proxy pods reach `0.0.0.0/0` (and `::/0` with `dual_stack`) except three groups: the internal ranges (`network.internal_cidrs`), the pod and service networks, and the node, node public and load balancer addresses. The rule names no pod and no namespace, and no cluster DNS: no cluster DNS is reachable from the egress namespace, so the proxy resolves names through `network.public_resolvers` (`dnsPolicy: None`).

## Values

Required keys have no default: a missing key stops the render with `BR_SANDBOX_MISSING_VALUE{key=...}`. Keys are snake_case; keys that are Kubernetes fields keep the Kubernetes name (`runtimeClassName`, `runAsUser`, `runAsGroup`, `terminationGracePeriodSeconds`, `imagePullSecrets` names, resource maps). `values.schema.json` has `additionalProperties: false` on every block with fixed keys: a key outside its place fails the render. Maps keyed by a name are checked entry by entry (`clients`, `clients.<client>.modes`, `pool.node_selector` with string values). One object takes any key: `keeper.settings`. All durations are in seconds. The keeper reads one JSON document that the chart renders from these keys; the document has the key names of the keeper, mapped as the Keeper document section says (for example `idle_ttl` is `idle_ttl_seconds` of each pool, and `save.ttl_seconds` is `save_ttl_seconds`). Two keys of this table are also keys of the document with the same name, `warm_max_age_seconds` and `idle_keep_min_state_bytes`; the keys of `keeper.settings` go into the document as they are.

Render errors: `BR_SANDBOX_MISSING_VALUE`, `BR_SANDBOX_MODE_UNKNOWN`, `BR_SANDBOX_SHARED_NAMESPACE` (two equal names among the system, sandbox and egress namespaces, or a runner namespace equal to an egress namespace), `BR_SANDBOX_NAME_TOO_LONG` (a namespace name over 63 characters), `BR_SANDBOX_SAVE_AGE_INVALID`, `BR_SANDBOX_EXEC_TIMEOUT_INVALID{key=exec_timeout_seconds}` (a null `exec_timeout_seconds`; `0`, a negative number, a string and a float are refused by the schema), `BR_SANDBOX_KEEPER_SETTING_COMPUTED{key=...}` (a `keeper.settings` key that the chart computes from another value), `BR_SANDBOX_POOL_INVALID` (floor above `max_sandboxes`), `BR_SANDBOX_EGRESS_DISABLED`, `BR_SANDBOX_CREDENTIAL_SET_MODE`, `BR_SANDBOX_ALLOW_MODE` (an `allow` list in mode `none` or `full`), `BR_SANDBOX_ALLOW_EMPTY{client=...,mode=allow}` (with `egress.enabled`, a mode `allow` with no `allow.domains` and no `allow.cidrs`: the adapter refuses that document, and a namespace that denies everything is mode `none`), `BR_SANDBOX_QUANTITY_INVALID` (a resource quantity with an unknown suffix), `BR_SANDBOX_RUNNER_IS_POD_IDENTITY` (a `runner.service_account` named `sandbox` with a `runner.namespace` that is a sandbox namespace: the runner identity is never the identity of the sandbox pods), `BR_SANDBOX_CREDENTIAL_HOSTS_EMPTY`, `BR_SANDBOX_CREDENTIAL_PLACEHOLDER_EMPTY`, `BR_SANDBOX_CREDENTIAL_PLACEHOLDER_DUPLICATE`, `BR_SANDBOX_CREDENTIAL_ENV_DUPLICATE`, `BR_SANDBOX_CREDENTIAL_ENV_RESERVED`, `BR_SANDBOX_CREDENTIAL_HOST_WILDCARD`, `BR_SANDBOX_CREDENTIAL_KEY_DUPLICATE`, `BR_SANDBOX_CREDENTIAL_REQUIRE_TLS` (`require` with an effective `require_tls`; set `require_tls: false` to use `require`), `BR_SANDBOX_PROXY_ADDRESS_DUPLICATE`, `BR_SANDBOX_PROXY_PORT_CONFLICT`, `BR_SANDBOX_PROXY_QUOTA`.

**Keeper document.** With `keeper.enabled`, the ConfigMap `br-sandbox-keeper-config` of the system namespace holds one JSON document under `config.json`, mounted at `/etc/br-sandbox/config.json`; `BR_SANDBOX_CONFIG` names it. The document has only keys of the keeper: `label_prefix`, `managed_namespace_selector` (`br.sandbox/managed=true`: the chart writes this label as a literal on the sandbox namespaces and on the selector of the admission bindings, and builds the selector from the label prefix; a test compares the selector with the label of every sandbox namespace and of those bindings, and checks that neither an egress namespace nor the system namespace carries it), `store_bucket`, `store_endpoint`, `store_region`, `store_path_style`, `listen_address`, `save_ttl_seconds`, `tombstone_ttl_seconds`, `warm_max_age_seconds`, `lease_duration_seconds`, `renew_deadline_seconds`, `retry_period_seconds`, and `pools`, one entry for each (client, mode): `id` (`{client}-{mode}`), `namespace`, `replicaset` (the name of the ReplicaSet of the pool), `min_replicas`, `max_replicas`, `refill_seconds`, `margin`, `idle_ttl_seconds` and `idle_keep_min_state_bytes`. The Lease namespace is the namespace of the pod, which is the namespace that holds the lease Role. A key of `keeper.settings` goes into the document as it is (`scale_down_cooldown_seconds`, `timezone`, `sweep_interval_seconds`, `lease_namespace`); the chart renders no `floors` for a pool; the keeper refuses an unknown key or a bad value when it starts, and the chart does not check them. A key that the chart computes from another value fails the render, so a value has one source. The adapter document (the ConfigMap `br-sandbox-config` of each sandbox namespace, see the next paragraph) holds the same constant `label_prefix` (`br.sandbox`, which is not a chart value) and the same chart value for `idle_ttl`, `idle_keep_min_state_bytes`, `save.ttl_seconds` and the four `store` keys, and no pool key, no warm age and no tombstone age. The warm age, the tombstone age, the pool keys, the three lease keys, `listen_address` and `managed_namespace_selector` are in the keeper document only. A test renders the chart with `ci/keeper-nondefault-values.yaml`, which sets each of these chart values away from its default (`label_prefix` is a constant, so it is not set), and checks that both documents carry exactly those values. The store credential is not in the document: it stays in the two variables `AWS_ACCESS_KEY_ID` and `AWS_SECRET_ACCESS_KEY`. The system namespace holds no ConfigMap `br-sandbox-config`. The ConfigMaps `br-sandbox-config` of the sandbox namespaces are the adapter documents. The pod template carries `br.sandbox/keeper-config-sha256`, the SHA-256 of the document, so a change of the document rolls the keeper pods. The keeper container declares the port `http` (`keeper.port`) and has a `livenessProbe` on `/livez` and a `readinessProbe` on `/readyz`; the chart does not change the `default-deny` policy of the system namespace. Not tested on a cluster: that the probes of the kubelet pass under `default-deny` (it depends on the network plugin; if they do not, the keeper pod does not become Ready). A scrape of `/metrics` by a pod needs a policy of the project.

**Adapter document.** The ConfigMap `br-sandbox-config` of each sandbox namespace holds one JSON document under `config.json`, with the flat keys of `SandboxConfigInput` of `br-runner-sandbox` and no other key: `namespace`, `client_id`, `pool_id` and `network_mode` (`none`, `allow` or `full`) from the (client, mode) of the namespace (`pool_id` is `{client}-{mode}`, the pool of the keeper document); `label_prefix`; `save_ttl_seconds`, `save_scope_paths` (`save.paths`), `restore_timeout_seconds`, `exec_timeout_seconds`, `idle_ttl_seconds` (`idle_ttl`) and `idle_keep_min_state_bytes`; `agent_container` (`agent`), `tools_path` (`{tools.mount_path}/bin/bsdtar`) and `seed_root` (`/skills`), and, only while `tools.seed_container.enabled` is true, `seed_container` (`tools.seed_container.name`) and `seed_tools_path` (`/sbx/bin/bsdtar`), each the value that the pod of the pool uses; `store_endpoint`, `store_bucket`, `store_region` and `store_path_style`. In mode `allow` the key `allowlist` holds `allow.domains` then `allow.cidrs` of the mode, the two lists that the proxy of the namespace allows; a mode with no list renders no `allowlist` key, and the adapter refuses mode `allow` with no list when it starts, so with `egress.enabled` the render fails with `BR_SANDBOX_ALLOW_EMPTY{client=...,mode=allow}` for a mode `allow` that has no `allow.domains` and no `allow.cidrs`. With `egress.enabled` false no list can be given (`BR_SANDBOX_EGRESS_DISABLED`): the namespace of mode `allow` is rendered without a proxy and its document has no `allowlist`, so the adapter refuses it; it cannot be used until egress is enabled and a list is given. The chart has no value for `save_zstd_level`, `open_timeout_seconds`, `save_timeout_seconds`, `claim_max_attempts` and `cold_create`: the document does not hold them and the adapter uses its default. The key `exec_timeout_seconds` is the bound of one `run` in the foreground, and the same key bounds the seed copy at an open; a command that needs longer uses the background form of `run`, which returns the id of the process and not its output. This is read from the code of the adapter and is not tested here or on a cluster. Before 0.3.0 the document had no such key, and the adapter, read from its code, then applied no bound to these two operations. A test renders the chart on each fixture, loads each document through `SandboxConfigInput` and `SandboxConfig::try_from`, and checks that the adapter holds the rendered value. `store_credentials` is never in the document and `kube_context` is not rendered; the credential comes from a Secret of the runner namespace, and the importer adds it (the chart renders no Secret). The only reader of this ConfigMap is the runner identity: the Role `br-sandbox-runner`, bound to `runner.service_account` of `runner.namespace`, has `get` on that name. No pod mounts it, and it holds no secret. The old key `config.yaml` is not rendered. The chart names the agent container `agent` and gives that name in `agent_container`; the default of the adapter is another name, `sandbox`, so a document without that key would name a container that the pod does not have. With `tools.seed_container.enabled` false the pod has no seed container, so the document holds neither `seed_container` nor `seed_tools_path`, and the adapter then uses its defaults `seed` and `/sbx/bin/bsdtar`; the failure of an open with a non-empty seed follows from the adapter code and is not tested here or on a cluster (the exec would name a container that the pod does not have), and the same holds for the statement that an open with an empty seed is not affected. The chart does not check `save.paths` against the rules of the adapter: the adapter refuses, when it starts, a list that does not hold `/work` (`ScopeWithoutWork`), a list in which one path holds or equals another (`ScopeNested`), a list in which a path holds or is held by `/skills`, the seed root (`SeedRootInScope`), and a path with a `..` part (`PathEscapes`), and the chart renders such a list as it is given.

Constants, not keys (a value that weakens one is a different chart): label prefix `br.sandbox`, `hostUsers: false`, seccomp `RuntimeDefault`, the seven capabilities, no service account token, no ingress, no port in a sandbox pod (the keeper declares `keeper.port`), Pod Security `baseline` enforced, `restricted` warn and audit, the loopback listeners (including the reload listener `127.0.0.1:9092`), the mount paths of the proxy pod, the numeric user and group of the proxy pod (65532, also its `fsGroup`) and the mount path of the CA certificate in the sandbox (`/etc/br-sandbox-ca`).

## Egress proxy

One proxy Deployment `br-sandbox-proxy` (label `br.sandbox/role=proxy`, `egress.proxy.replicas`) in each egress namespace, with its Service, the ConfigMap `br-sandbox-proxy-config` (file `proxy.yaml`) and the ConfigMap `br-sandbox-proxy-ca`. The pod is made by the Deployment controller. It has no ServiceAccount token, no Role and no RoleBinding exist in the namespace, and the pod runs with `hostUsers: false`, a numeric non-root user, `drop ALL`, a read-only root file system, seccomp `RuntimeDefault`, `allowPrivilegeEscalation: false`, `dnsPolicy: None` with `network.public_resolvers`, `enableServiceLinks: false`, a writable `/tmp` as an `emptyDir` of 16Mi, a readiness and a liveness probe (TCP on the tunnel port, every 5 seconds), and the requests and limits of `egress.proxy.resources`. The image is `egress.proxy.image` by digest, with the mirror prefix; the pull secrets apply.

**Config of the proxy.** Standalone: the render holds no control-plane token, no tenancy block, no telemetry endpoint, no response-retry handler and no host of the vendor. The built-in DNS server is off. The tunnel listener (CONNECT) is on `egress.proxy.port`; the direct HTTP and HTTPS listeners, the metrics listener and the reload listener (`127.0.0.1:9092`, constants) bind the loopback address of the pod, so no sandbox policy reaches them (and `ingress-tunnel` opens the tunnel port only). TLS mode `mitm`: the CA certificate comes from the ConfigMap `br-sandbox-proxy-ca`, the CA key from the Secret named by `proxy.ca.key_secret`. Transforms in fixed order: `allowlist`, then `secrets` (only with a credential set). Mode `allow`: `allow.domains` and `allow.cidrs`, with or without a credential set. Mode `full` with a credential set: the pattern `*`, so every public name is allowed; the deny list still applies. `upstream_deny_cidrs` is the deny list of the `egress-proxy` policy (internal, pod, service, node, node public and load balancer lists, and the IPv6 ones with `dual_stack`) plus the loopback ranges. There is no response scrub transform.

**The proxy address in the sandbox.** A sandbox resolves nothing (resolver `127.0.0.1`, no DNS rule), so the variables hold an IP: `http://{proxy.cluster_ip}:{egress.proxy.port}`, the fixed `clusterIP` of the Service. The address must be free and inside `network.service_cidr`; the API server refuses the Service otherwise (documented behaviour of Kubernetes, not measured here). The chart does not check that the address lies in that range. The `clusterIP` of a Service cannot be changed in place (documented behaviour of Kubernetes, not measured here): changing `proxy.cluster_ip` needs the proxy Service of that mode deleted first, or a forced replace by the deploy tool; the chart does not do it. Two namespaces with the same address fail with `BR_SANDBOX_PROXY_ADDRESS_DUPLICATE`. The sandbox policy selects the proxy pods, not the address: it relies on the translation of the Service address to a pod address before the policy applies; that is not proved offline.

**CA flow.** The CA certificate is a value (`proxy.ca.certificate`), rendered as the ConfigMap `br-sandbox-ca` in the sandbox namespace and mounted read-only at `/etc/br-sandbox-ca` (file `ca.crt`) in the agent container; the variables of `egress.ca.env_names` point to it. The CA reaches the tools of the sandbox only through that file and those variables: the system bundle of the sandbox image is not changed, so a tool that ignores those variables refuses the proxy certificate. The CA key exists only in the Secret of the egress namespace, mounted in the proxy pod. No sandbox pod has a Secret volume, a `secretKeyRef` or a `secretRef`, and the admission policy refuses all three (the policy expressions were not executed, see Admission policy).

**Credentials.** The sandbox receives the placeholder in the variable `env_name`; the real value is the file `key` of the Secret `credential_set.secret_ref`, mounted read-only in the proxy pod only (source type `file`). The set is rendered in mode `allow` (the `secrets` transform comes after the allowlist, so the host must be on the allow list too) and in mode `full` (every public name). The swap of a placeholder was measured on the pinned proxy image (0.61.0) in mode `full` with a credential set only, in a Bearer `Authorization` header; the swap in mode `allow` is the documented behaviour of the proxy product, not measured here, and is listed under Not proved offline. By the documented behaviour of the proxy product, not measured here, each placeholder is bound to its `hosts`, `require_tls` (default true) keeps a bound value off plain HTTP, and `require` makes the proxy answer 403 to a bound host that sends no placeholder. The chart refuses `require` together with `require_tls` (`BR_SANDBOX_CREDENTIAL_REQUIRE_TLS`). The intended path for git is HTTPS with the token as placeholder; git over ssh is not offered. The form measured on the pinned proxy image (0.61.0), in mode `full` with a credential set, is a plain HTTPS GET with a Bearer header; no git client was used. The swap inside a `Authorization: Basic` header, the form that git sends, is not claimed: the chart renders the rule and the offline suite cannot prove how the product treats that header.

**Limit.** A bound host that sends a credential value back shows it to the sandbox (no scrub exists; the proxy has no response scrub). Measured on the pinned proxy image (0.61.0) in mode `full` with a credential set: a response body that echoed the `Authorization` header carried the real value to the client. The chart claims nothing else about credentials.

**Rotation and config changes.** A change of the proxy config (an allow list, the deny list, a credential rule) or of the CA certificate of a (client, mode) changes an annotation of the pod template (`br.sandbox/proxy-config-sha256`, `br.sandbox/proxy-ca-sha256`: the SHA-256 of the rendered config and of the CA certificate), so `helm upgrade` rolls the proxy pods. The chart makes no checksum of content that it does not render: a change of the content of the credential Secret, of the CA key Secret or of the ConfigMap of `egress.proxy.upstream_ca` does not change the pod template and does not roll the pods. By the documented behaviour of the proxy product, not measured here, the proxy re-reads a `file` source at a reload call (`POST /v1/reload`, bearer key from `egress.proxy.reload.key_secret`); for any other content the chart claims a restart only. The project rolls the pods itself, by a restart of the Deployment or by the reload call, through its own gesture. The reload listener is `127.0.0.1:9092` in the pod: only a caller inside the pod reaches it, and nothing in the chart calls it (no identity of the chart has `pods/exec` in the egress namespace).

**Trust of the proxy for upstream servers.** The proxy trusts the system roots of its image. With `egress.proxy.upstream_ca` set (`config_map`: a ConfigMap of the egress namespace; `key`, default `ca.crt`), the chart mounts that key read-only at `/etc/iron-proxy/trust/` and sets `SSL_CERT_FILE` on the proxy container to the file. The project creates the ConfigMap in each egress namespace (a missing ConfigMap keeps the pod from starting); the file holds certificates, not secrets. Measured on the pinned proxy image (0.61.0): the roots of the file are added to the roots of the certificate directory of the image (`/etc/ssl/certs`); they do not replace them. A certificate authority placed only in that directory stayed trusted while `SSL_CERT_FILE` named another file; a private authority that was in neither was refused (`x509: certificate signed by unknown authority`); the file alone is enough to trust a private authority, and the public roots of the image directory stay trusted. Nothing was measured about the default bundle file of the image when `SSL_CERT_FILE` is set. Unset, nothing is rendered.

**Targets named by a name.** Measured on the pinned proxy image (0.61.0) with the config of this chart in mode `full` with a credential set: a client sends `CONNECT git.example.test:443` with the server name `git.example.test`; the proxy resolves the name with the OS resolver of the proxy pod (`network.public_resolvers`, `dnsPolicy: None`), dials the address, and swaps the placeholder in a Bearer `Authorization` header with the value of the credential file (the audit line of the proxy says `swapped ... header:Authorization`). A project that wants a private test server needs a DNS that answers its names (a resolver of `network.public_resolvers` that knows them) and a certificate authority that the proxy trusts (`egress.proxy.upstream_ca`).

**Targets named by an IP literal.** An `allow.cidrs` entry allows the `CONNECT` to an address: the render puts the entries of `allow.cidrs` into the `allowlist` transform beside the domains, and the render needs no name for it (the DNS server of the proxy is off). TLS to an IP literal does not work. Measured on the pinned proxy image (0.61.0): the proxy needs a name in the TLS server name (SNI) to make a leaf certificate, and clients send no SNI for an IP, so the proxy logs `TLS handshake for <ip>:443: no SNI provided` and the client gets a TLS internal error. Plain HTTP to an IP literal is not claimed: the sandbox checks do not use it. Use a name. The deny list of the policy is rendered into `upstream_deny_cidrs`. One value, `network.internal_cidrs`, feeds both the `egress-proxy` policy and the deny list of the proxy: a range taken out of it is taken out of what that value contributes to both lists. Whether the range is then open depends on the other lists that the chart builds, and the proxy list always holds the loopback ranges, so read the rendered lists. Change it on a test cluster only.

**Not proved offline.** The suite renders and reads objects. It does not start the proxy: that the product accepts this config (a `*` pattern, an empty allow list, the listener addresses), that it checks the deny list at connect time for an address, that it makes no call to its vendor, the swap of a placeholder (measured by hand in mode `full` only), the swap of a placeholder in mode `allow`, that each placeholder is bound to its `hosts`, that `require_tls` keeps a bound value off plain HTTP, that `require` makes the proxy answer 403 to a bound host that sends no placeholder, that the proxy re-reads a `file` source at a reload call, the 403 and 502 answers, the translation of the Service address, the refusal by the API server of a change of the `clusterIP` of a Service in place (documented behaviour of Kubernetes, not measured here), the user namespace of the proxy pod, the file modes of the Secret files in a running pod (the render sets `defaultMode: 288`, octal 0440, on the CA key volume and on the credential volume and the suite reads that value; it does not show what the kubelet gives the files), the refusals of the runner and keeper identity by the real API server in an egress namespace (the suite shows only that the render holds no Role, no RoleBinding and no binding subject there), and the CEL of the admission policy are not checked by this suite and are left to cluster tests that this repository does not hold. The suite does not prove that the proxy refuses a name that resolves to an internal address: no test resolves such a name, and a change of the DNS answer between the check of the address and the dial is a property of the proxy product, not measured here. The probes of the proxy pod come from the node: the chart does not test that the network plugin lets them through `default-deny` and `ingress-tunnel`; if it does not, the proxy does not become Ready and the mode has no egress. Two tests are also not made: the test of each barrier alone (the chart rendered with one barrier only), and the proof of the pivot barriers of mode `full` (a test server at an internal address that records its connections); no such test exists in this repository at this version and none was executed. The behaviours measured above (name target, IP literal over TLS, the swap in a Bearer `Authorization` header in mode `full`, an echoed value) were measured once by hand on the pinned image (0.61.0); the suite does not start the proxy.

What the chart relies on, and does not test: that a proxy with no token set makes no call to its vendor; the `egress-proxy` policy lets the proxy reach public addresses, so the policy does not stop such a call. A ten-minute idle capture of the pinned proxy image (0.61.0) on an isolated network showed 0 IPv4 packets; IPv6 frames were counted and not decoded; the ten minutes were taken with the config of mode `full` only. That does not cover a call after a rare event or on another version; a new digest needs a new capture.

**Limits of the measurements.** Every capture named as measured on the pinned proxy image (0.61.0) was taken with the arm64 image of the digest only; the amd64 image of the digest was not started. All captures were taken in containers on a network with no route out, not in a cluster.

## Modes

| Mode | NetworkPolicies of the namespace | Pod DNS |
|---|---|---|
| `none` | `default-deny` only (ingress and egress, every pod) | `dnsPolicy: None`, nameserver `127.0.0.1` |
| `allow` | `default-deny` and `egress-allow`: sandbox pods reach only the pods `br.sandbox/role=proxy` of the egress namespace of the same (client, mode), TCP on `egress.proxy.port`; namespace and pod are selected in the same rule item; no DNS | same as `none` |
| `full` | `default-deny` and `egress-full`. With a credential set: the same rule as mode `allow`, nothing else, and the pod resolver is `127.0.0.1`. Without: `0.0.0.0/0` except internal, pod, service, node, node public and load balancer lists; with `dual_stack` also `::/0` except `fc00::/7`, `fe80::/10` and the IPv6 addresses. No rule names a pod or a namespace, so no cluster DNS | nameservers `network.public_resolvers` |

The rows of the table state the rules of the policies. They hold for a pod once the network plugin enforces them; they say nothing about the first seconds of a fresh pod (see The enforcement window, in Network check).

No policy of a sandbox namespace or of the system namespace has an ingress rule; the only ingress rule of the chart is `ingress-tunnel` of an egress namespace. The sandbox side selects `br.sandbox/role=sandbox`, never the pool label, so a claimed pod keeps its path. The only egress rule of a sandbox in a mode with a proxy leads to the proxy pods, so, once the network plugin enforces the policies, a sandbox has no other path (fail closed in that steady state; a fresh pod is not covered during its first seconds, see The enforcement window). A tool can send DNS to any public host in mode `full`; only the pod resolver is fixed.

A bound host that sends a credential value back shows it to the sandbox (no scrub exists; the proxy has no response scrub). The chart claims nothing else about credentials.

## The pod

Agent container `agent`: the project image, command `{tools.mount_path}/bin/pause`, user `runAsUser` with `runAsNonRoot: true` (the init container `tools-init` runs as the same user with the same flag), env `HOME=/home/agent`, volumes `tools` (read-only), `/work`, `/home/agent`, `/skills` (read-only). Init container `tools-init` (tools image): `/sbx/bin/bsdtar -x -p --no-same-owner -f /sbx/tools.tar -C {tools.mount_path}`. All containers drop ALL and add `CHOWN, DAC_OVERRIDE, FOWNER, FSETID, SETUID, SETGID, KILL`. Volumes are `emptyDir` with a size limit (a `configMap` only for the check pod).

**Seed container (contract for the library `br-runner-sandbox`).** Name `seed` (key `tools.seed_container.name`), image `br-sandbox-tools`, command `/sbx/bin/pause`, root user inside the user namespace, `readOnlyRootFilesystem`, no port, no shared process namespace, same seven capabilities. The library `br-runner-sandbox` writes the seed through `pods/exec` into this container, mount path `/skills`, program `/sbx/bin/bsdtar` (in the agent container the same program is `{tools.mount_path}/bin/bsdtar`, default `/opt/sbx/bin/bsdtar`). The agent mounts `/skills` read-only, so a non-root agent cannot change the seed. `tools.seed_container.enabled: false` removes the container; then `/skills` is writable by the agent and the seed is only the weak form. Its resources are small keys of their own: whether they count in the size of the pool is open.

## Runner role

The Role `br-sandbox-runner` of each sandbox namespace is the contract for the adapter. It binds the `runner.service_account` of `runner.namespace`. Rules: `pods` get, list, watch, patch, create, delete; `pods/exec` get and create; `replicasets` get, list, watch (the adapter reads the condition of the pool); `configmaps` get on `br-sandbox-config` only (the adapter document). The keeper Role of the same namespace (with `keeper.enabled`) has `pods` get, list, watch, delete; `replicasets` get, list, watch, patch; `replicasets/status` patch; `events` create. It has no `pods` patch. No identity of the chart has a Role in an egress namespace.

The runner Role holds `get` and `create` on `pods/exec` in each sandbox namespace. Every sentence of this paragraph about the behaviour of Kubernetes is read from public pages and is not tested on a cluster. The pages are: the Kubernetes feature gates reference (https://kubernetes.io/docs/reference/command-line-tools-reference/feature-gates/, the gate `AuthorizePodWebsocketUpgradeCreatePermission`); KEP 4006 of kubernetes/enhancements (https://github.com/kubernetes/enhancements/tree/master/keps/sig-api-machinery/4006-transition-spdy-to-websockets); the issue kubernetes/kubernetes#78741 (https://github.com/kubernetes/kubernetes/issues/78741); and the Kubernetes RBAC reference (https://kubernetes.io/docs/reference/access-authn-authz/rbac/). A client that opens the exec stream with a POST request (SPDY) needs `create`, and the WebSocket handshake is a GET request (feature gates reference, KEP 4006). The feature gates reference and KEP 4006 say that, while the feature gate is on, a WebSocket upgrade on `pods/exec`, `pods/attach` and `pods/portforward` must also be authorized to `create` the subresource; the feature gates reference lists the gate as beta since 1.35, on by default. The issue kubernetes/kubernetes#78741 says that a WebSocket exec was allowed with `get` on `pods/exec`, and KEP 4006 says that RBAC policies that only grant the `get` verb unexpectedly allow `exec`, `attach` and `port-forward` once the handshake is a GET request; that `get` alone was enough on every Kubernetes before 1.35 is our inference from these pages, not a sentence of them. The adapter uses a WebSocket: this is read from the code of the adapter (`kube` with its `ws` feature), and not tested on a cluster. So the adapter needs `get`, and, on Kubernetes 1.35 or later while the feature gate is on (it is on by default from 1.35), it needs `create` as well. The verb `get` in the `pods/exec` rule adds no read of `pods`, of `pods/log` or of `secrets`: the RBAC reference names each resource and each subresource separately (`pods` and `pods/log` in the example of that page).

## Admission policy

One policy and binding per (client, mode); values (size, runtime class, repositories) are inlined. The binding matches the namespace by `br.sandbox/managed=true` and by name. It matches every pod, `CREATE` and `UPDATE`, and fails closed.

- A pod passes if it is `role=sandbox` and follows the rules below. Any other role, or none, is refused (`BR_SANDBOX_ROLE`), `role=proxy` included: a proxy pod does not live in a sandbox namespace, it lives in the egress namespace, which the policy does not bind. The role cannot change (`BR_SANDBOX_ROLE_IMMUTABLE`).
- Rules of a sandbox pod: 1 `hostUsers` false (`USERNS_REQUIRED`); 2 no host network, PID, IPC, port (`HOST_NAMESPACE`); 3 only `emptyDir` and `configMap` volumes, no `secretKeyRef`, no `secretRef` (`VOLUME_FORBIDDEN`); 4 drop ALL, add only the seven (`CAPABILITY`); 5 no privilege, no escalation, seccomp `RuntimeDefault` on the pod and, when a container sets a profile, on that container (`PRIVILEGE`); 6 cpu, memory and ephemeral-storage requests and limits on every container, not above the size of the pool (`RESOURCES`); 7 every image from an allowed repository (project image, tools image, check image, each with the mirror) with a tag or a digest (`IMAGE`); 8 no token, runtime class equals the chart value (`TOKEN_OR_RUNTIME`); 9 on update the security contexts, resources, volumes and `hostUsers` stay (`IMMUTABLE`); 10 every container of the three lists (`containers`, `initContainers`, `ephemeralContainers`) sets `runAsNonRoot: true` and a `runAsUser` above 0 in its own `securityContext`, and the pod does not share its process namespace (`RUN_AS_NON_ROOT`).
- Patch rules (`BR_SANDBOX_LABELS`): a patch changes only `br.sandbox/` keys of labels and annotations; `role` and `pool-id` never change; a claimed pod never leaves `claimed`.
- Init and seed containers are containers of the pod and follow rules 4 to 7 and 10. Rule 10 is the only rule that reads `ephemeralContainers`: rules 4 to 7 read `containers` and `initContainers`, rule 9 reads `containers`. An ephemeral container is checked for non-root and for nothing else: the policy does not refuse a non-root ephemeral container that is privileged, adds capabilities, uses any image or asks any size. No Role of the chart (runner, keeper, check) holds a verb on `pods/ephemeralcontainers`, so none of these identities can add an ephemeral container; an identity of the cluster that holds the verb can, and for it rule 10 is the only limit.
- Rule 10 has two exceptions, both exact. The seed container of the regular container list (`containers`) passes by its name (`tools.seed_container.name`) and by its image, which is exactly the tools image that the chart renders (the same string, with the mirror prefix when there is one); it must still set `runAsUser` 0, have a read-only root file system and no port, and rule 4 still limits it to the seven capabilities. A container with the seed name and another image is refused. An init container or an ephemeral container with the seed name, the tools image, uid 0, a read-only root file system and no port is refused too: the exception does not apply to those two lists, which must satisfy the plain non-root condition. The pods of the network check, which have uid 0, pass by the user name of the ServiceAccount that makes them, `system:serviceaccount:{system namespace}:br-sandbox-netcheck`, and by no label or name; they still must not share the process namespace. With `network_check.enabled: false` the rule has no such exception, and with `tools.seed_container.enabled: false` it has no seed exception. The policy also watches `UPDATE` of `pods/ephemeralcontainers`, so an ephemeral container as root is refused.

**What the policy does not hold.** The seed is written by the adapter through `pods/exec` into the seed container, which runs as root. No rule protects the seed against an adapter that is compromised: it can write any content to `/skills`. The policy holds the shape of the pods, not the content of their files.

**Upgrade from a pool of chart 0.1.0 to 0.1.1.** Rule 10 runs on every `UPDATE` of a `role=sandbox` pod. The agent container of any pod of a sandbox namespace made by chart 0.1.0, warm or claimed, has no `runAsNonRoot`, so after the upgrade the next `UPDATE` of that pod is refused until the pod is recreated: the claim patch for a warm pod, a later label or annotation update for a claimed pod. A ReplicaSet does not recreate running pods when its template changes, and a claimed pod is not owned by the ReplicaSet. Before the claim path is used, delete the old warm pods of every sandbox namespace; the ReplicaSet recreates them from the new template. For a claimed pod, let the agent finish and delete the pod, or delete it at once.

**Upgrade to 0.2.0.** With `egress.enabled: true`, a warm pod of a mode with a proxy that was made before the upgrade keeps its old template (no proxy variables, no CA file, no placeholders), so it has no working egress until it is recreated: a ReplicaSet does not recreate running pods when its template changes. After the upgrade, delete the old warm pods of every sandbox namespace of a mode with a proxy; the ReplicaSet recreates them from the new template. A claimed pod made before the upgrade keeps its old template too, and it is not owned by the ReplicaSet, so deleting the old warm pods does not reach it: let the agent finish and delete the pod, or delete it at once. Where the keeper is deployed, it deletes a warm pod older than `warm_max_age_seconds` (default 1800).

A cluster test of the refusals of an unlabelled pod, of a `role=proxy` pod and of a relabel of the role, with the runner service account, in a sandbox namespace, and of the refusal of rule 10 by the runner service account, is to be made; no such test exists in this repository at this version and none was executed. The CEL of the admission policy is not compiled offline, so at this version it has been neither compiled nor executed on a cluster.

## Image contract

**The agent image.** Any Linux image with `/bin/sh`, `cat` and `find`, for the architecture of the nodes. Nothing else: no agent binary, no `tar`, no user entry, no `ps`. The tools that the sandbox needs (`bsdtar`, `pause`) come from `br-sandbox-tools`. The project puts one registry link in `image`. Example: `br-sandbox-python` (Python 3.12, pandas, openpyxl, python-docx, python-pptx, LibreOffice), the test and reference image of this repository only; each project defines its image.

**A new push under one tag.** A tag pulls at each pod creation (`imagePullPolicy: Always`). A warm pod is used one time, so the pool takes the new image as it refills, and the keeper deletes a warm pod older than `warm_max_age_seconds` (default 1800). A quiet pool has the new image in 30 minutes at most. A digest is advised for production; with a digest the pull policy is `IfNotPresent`.

**The check image.** `network_check.image` runs the Job pod and every probe pod. It needs `sh`, `kubectl`, `nc`, `cat`, `sed`, `tr`, `mktemp`, `awk`, `sleep` and `date`: the programs that the script calls at this version, besides the builtins of `sh`. A test checks the script against a fixed list of candidate program names; it does not parse every command of the script. The probe relies on this `nc` behaviour: it sends its input, then keeps reading the reply until the proxy closes the connection; `-w` is an idle timeout (no data for that many seconds ends it); it exits when the proxy closes the connection. `nc` builds differ on these points. The suite uses a stub of `nc`; no real `nc` build is exercised by the suite. The real probe image and its `nc` were not started at this version. The first cluster test must confirm that the tools the probe needs exist there and that `nc` behaves as the probe expects (it reads until the proxy closes, `-w` is an idle timeout, it exits on close). It runs the check Job and the check pods. No image of this repository has them; the project or the cluster test sets the value. The image is chosen by the project. One image was measured by hand on a test cluster, and no test of this repository proves it: the image `rancher/k3s` has no `nc`.

## Network check

The Job `br-sandbox-netcheck-{run_id}` (and an optional CronJob) lists the nodes, services and pods through the API, builds targets (the `targets` values, a ClusterIP, a pod IP, each node address on 10250 and 6443, the API service, the cluster DNS service, a `.svc.cluster.local` name), and probes from the Job pod (the control) and from a probe pod of each namespace. The probe pod is made from the pool pod template (no token, root inside the user namespace); rule 10 of the admission policy lets it through by the identity of the check ServiceAccount. Before the Job creates the probe pod of a namespace it deletes a pod of the same name, `br-sandbox-netcheck-probe`, that an earlier Job left there (a Job that was killed does not delete its probe pod), and waits for it to be gone, for at most 60 seconds; a leftover pod that the delete does not remove (the delete command fails for any cause, the wait of 60 seconds ending without the pod gone being one) gives one `probe_pod` object for that namespace (`expected` `absent`, `observed` `not_deleted`), the Job makes no probe in it and fails. The Role of the check identity is not changed: it already holds `delete` on pods in the sandbox namespaces. One JSON object per probe: `{net, mode, target, kind, expected, observed, control}`; `kind` is `tcp`, `connect`, `target_class`, `node_list`, `probe_pod` or `precondition`. By kind: `tcp` carries `observed` `refused`, `reached` or `no_result`, `control` `ok` or `control_unavailable`, `refused_after_seconds` and `limit_seconds`; `connect` carries `observed` `refused`, `reached` or `no_result` and `control` `not_applicable`; `target_class` carries `observed` `missing` and `control` `ok`; `node_list` carries `observed` `stale` and `control` `ok`; `probe_pod` carries `expected` `absent`, `observed` `not_deleted` and `control` `not_applicable`; `precondition` carries `observed` `invalid` or `missing` and `control` `not_applicable`. The Job fails on any `reached` (a probe that is still reached when the limit `network_check.enforcement_wait_seconds` is checked), any `control_unavailable`, a missing result, a node address that is not in the three node lists, a target class with no target, a `probe_pod` object, and at once, before any probe pod is created and with exit status 2, on a `precondition` object (see The enforcement window). The classes are `targets` (at least one entry of `network_check.targets`), `node_kubelet`, `node_api`, `api_service`, `dns_service`, `cluster_name` and `pod` (a pod IP with a declared container port); a missing class is one object with `kind` `target_class` and `observed` `missing`. For a (client, mode) in mode `allow` with a proxy the probe pod also sends `CONNECT` through the proxy, to each target and to `network_check.offlist_host`, and reads the status line of the answer to the `CONNECT`. The status code is the second field of the status line, compared as a whole field (`HTTP/1.1 200 x 403 y` is read as 200); a status line with no three-digit code is `no_result`. The verdict is `refused` when the answer is 403 or 502, `reached` when it is 200, and `no_result` for any other answer or no answer. The Job fails on any verdict other than `refused`. Captured on the pinned proxy image (0.61.0), mode `allow`: an IP address that is not on the list and an internal IP address both got 403 at the `CONNECT`; a name that is not on the list was not captured at the `CONNECT`. The Job does not probe the path through the proxy in mode `full`. Captured on the pinned proxy image (0.61.0), mode `full` with a credential set, in containers on a network with no route out: the proxy answered 200 to every `CONNECT` and refused only at the first request inside the tunnel, with a 502 that a reached target which does not speak HTTP also gave, so a probe from the sandbox side cannot give an exact verdict. On a deployed cluster the Job therefore does not prove the pivot barriers of mode `full`: that proof, a test server at an internal address that records its connections and sees none after a request through the proxy, is to be made on a test cluster; no such test exists in this repository at this version and none was executed. What this Job proves is the direct TCP probes of the sandbox pod, in the three modes, and the refusal at the `CONNECT` in mode `allow`. In mode `allow` the Job sends each `CONNECT` once, with all barriers in place: a 403 can come from the allowlist alone, before the deny list or the network policy acts, so the Job does not show that the deny list or the policy would refuse the target if the allowlist were absent. That test (each barrier alone), which renders the chart with only one barrier and runs the check against it, is to be made on a test cluster; no such test exists in this repository at this version and none was executed. One object per probe with `kind` `connect` and `control` `not_applicable`; `expected` is `refused`. The probe has no positive control: a proxy that refuses everything (a broken allow list) also passes the off-list check, so that a listed host is reached is left to a cluster test that this repository does not hold, not checked by this Job. The pod targets leave out the pods labelled `br.sandbox/role=proxy`.

**The enforcement window.** A direct TCP probe of the probe pod is tried again every second until it is refused or until `network_check.enforcement_wait_seconds` (an integer from 1 to 999999999, default 60) has passed, counted from the start of the probe script in the pod. The limit is checked between two tries, never during one: under a policy that drops the packets a try waits up to 2 seconds for its `nc -w 2` timeout, and a sleep of 1 second comes between a check below the limit and the next try, so a probe can go on up to 3 seconds after the limit; a refusal in that time reads as `refused`, and its `refused_after_seconds` can then be above `limit_seconds`. A printed time is the difference of two readings of `date +%s`, in whole seconds, so it differs from the real elapsed time by less than 1 second. `refused_after_seconds` is the time from that start to the first refusal of the target. The start is one value for the whole probe pod, not one for each target, and the limit is counted from it too: the limit is one budget for the pod, a later target gets what is left of it, and once it is spent each remaining target is tried once. The `nc -w 2` wait of every probe that is dropped counts in the elapsed time: under a policy that resets the connection (REJECT) a probe that is refused at once reports about 0; under a policy that drops the packets (DROP) each probe waits for its `nc -w 2` timeout before it reads as refused, so the k-th target of the pod reports about 2 times k seconds even when it was refused at its first try, and a value of 40 does not tell a late policy from 20 dropped probes. A probe still reached at the limit has `observed` `reached`, `refused_after_seconds` the text `not refused` and `limit_seconds` the limit, and the Job fails. What `refused` means: `nc` exited with any non-zero status. That covers a reset, the timeout of a dropped probe (a drop is read as a refusal on purpose: the policy stops the traffic), a name that does not resolve and an `nc` that fails for another reason. The probe does not tell these causes apart. In the probe pods the resolver is the one of the mode (see Modes), so the `cluster_name` target is expected to read `refused` because its name does not resolve there, and not because of a policy; that was not measured. One cause is told apart: at the start, before any probe, the script runs `command -v` for `nc`, `sleep` and `date`, in that order, and for the first one that is not found prints one `precondition` object (`target` the name of the program, `observed` `missing`) and exits with status 2; it does the same for a `NETCHECK_ENFORCEMENT_WAIT` that is not an integer from 1 to 999999999 (`observed` `invalid`). An `nc` that exists but is broken is caught only by the positive control: the Job pod runs the same image as the probe pods (`network_check.image`) and the same `nc` call, so a broken `nc` there gives `control_unavailable` and fails the Job. The control and the probe pods share the check image, and that sharing is what the argument rests on; a probe pod run with another image would lose it. The positive controls (from the Job pod) are tried once and never again, and the `CONNECT` probes in mode `allow` are tried once. Why: on a network plugin that enforces a network policy some time after the start of a pod, a fresh pod reaches internal targets for a short time. This was measured on a test cluster with flannel and the kube-router network policy controller: the policy started some seconds after the pod; a probe sent at once reached 2 of 2 targets, the same probe sent 30 seconds later reached 0. A probe at once therefore failed the Job although the policy worked. What the Job proves is the state after enforcement. A window exists in which a fresh sandbox pod can reach internal targets, and the chart does not close it; for each probe the Job reports `refused_after_seconds` and `limit_seconds`; `refused_after_seconds` is the time from the start of the probe script to the first refusal of that probe, it is not a measure of the length of the window (it carries the `nc -w 2` waits of the probes that were dropped before it), and the report does not tell the length of the window. The window was measured with that one network plugin; the time it takes on another plugin, or on a loaded cluster, was not measured, and the real behaviour of kube-router is not reproduced by the offline suite, which uses a stub of `nc` that reaches the first calls and then refuses.

The network check identity reads the pod specs of the whole cluster (a cluster-wide `get` and `list` on `pods`, `nodes`, `services` and `endpoints`) to pick its targets; its rights to create and delete pods and to read pod logs are bound in the sandbox namespaces only.

## Why

| Thing | Why it is the way it is |
|---|---|
| Namespace per (client, mode) | A mode cannot mix; the namespace checks hold by the namespace and not by a label. |
| The policy matches every pod | A pod without `role=sandbox` would escape and a runner with `pods create` could mount a Secret. |
| Proxy pods and their Secrets in a second namespace | The runner holds `pods/exec` and `pods` patch in the sandbox namespace; a proxy pod there would let a compromised runner read the credential value and the CA key. No identity of the chart has a right in the egress namespace. |
| Egress namespace without `br.sandbox/managed` | The admission policy of a sandbox namespace accepts `role=sandbox` pods only; it must not bind the proxy namespace. |
| Policy per namespace | The size and the repositories are inlined, so a pool size is a single key. |
| `hostUsers: false` fixed | Root in the pod is a high host user; the seven capabilities hold only inside. |
| `pause` from the tools mount | The agent image has no reaper; an orphan stayed alive after SIGTERM with `sleep infinity`. |
| Seed in a second container | `pods/exec` cannot choose a user; a root writer is needed so that a non-root agent sees a read-only seed. |
| One value, one source for the keeper and the adapter | `label_prefix` is a constant (`br.sandbox`), the same in both documents and not a chart value; the store keys, the save age, the idle time and the idle threshold are rendered into both documents from the same chart value, and a test with values that differ from their defaults checks both documents; the tombstone age, the warm age, the pool keys, the lease keys, the port and the selector are in the keeper document only. A `keeper.settings` key that the chart computes fails the render, so no second value can disagree. |
| The adapter document is proved by the real type | `crates/br-runner-sandbox/tests/chart_config.rs` renders the chart with `helm template` on each fixture, loads the document of each sandbox namespace through `SandboxConfigInput` and `SandboxConfig::try_from`, and refuses a key that is not in the table of the adapter; a misnamed key fails that test, not the runner at start. |
| The keeper document is proved by the real type | `crates/br-sandbox-keeper/tests/chart_config.rs` renders the chart with `helm template` and loads the document through `KeeperConfig::from_json`; a key that the keeper does not know fails that test, not the pod at start. |
| No `spec.replicas` | The keeper is the only writer of the replica count; a value rendered by the chart would be reset at each `helm upgrade`. A pool starts with one replica (the ReplicaSet default) until the keeper runs; `floor` is read by the keeper, not applied by the chart. |
| Quota = size x (`max_sandboxes` + `extra_pods`) + seed container resources x `max_sandboxes` (when `tools.seed_container.enabled`) | The refill must not be refused: each sandbox pod holds the agent and the seed container, and the extra pods hold one size each. The init container does not add: a pod counts the larger of its init containers and the sum of its containers. |
| Fixed `clusterIP` for the proxy | A sandbox has no DNS, so the address in `HTTPS_PROXY` must be known at render time; an address that the cluster assigns is not. |
| Loopback listeners, one open port | Only the tunnel port is open to a sandbox; the reload, metrics and direct listeners must be reached by no pod. |
| Pattern `*` in mode `full` with a credential set | The proxy is needed for the swap; names stay open as in mode `full`, and the deny list closes the internal ranges. |
| Seed exception by name and image | A name alone would let a pod run any image as root in a container called like the seed. |
| Check exception by user name | The probe pods run as root, so rule 10 admits them by the ServiceAccount that makes them; a label or a name can be set by any identity that creates a pod. |
| Selects `role`, never `pool` | A claim changes `pool`; the network path must not move. |
| `default-deny` in the system namespace only with keeper or check | An empty chart adds no policy there. |
| `egress-netcheck` allows all egress | The check must try to reach internal targets; the Job holds a read role, so it runs on demand. |
| Mirror is a prefix | `{mirror}/{reference}`; a mirror that rewrites the host is done by the mirror itself. |
| Label rule covers annotations | A runner may patch only `br.sandbox/` keys; a CNI that annotates the main pod resource would need an exception (to check on a cluster; no such check has been executed at this version). |

## Needs of the cluster (not done by the chart)

`kubelet` in `/etc/subuid` and `/etc/subgid` on each node; the Kyverno exclusion for namespaces with `br.sandbox/managed=true` (without it mode `none` is not possible) and for namespaces with `br.sandbox/egress=true` (the default network policy of the cluster would add its allow rules there, and the egress namespace would no longer follow `ingress-tunnel` and `egress-proxy`); the bucket with its lifecycle rule; the sealed Secret of `store.credentials_secret`. Each Secret named in `pull_secrets` in every sandbox namespace and in the system namespace, and in every egress namespace (an image pull reads the Secret of the namespace of the pod; the chart renders no Secret). Policy objects need Kubernetes 1.30 or later (ValidatingAdmissionPolicy v1).

A node needs a kubelet with subordinate id ranges (`/etc/subuid` and `/etc/subgid`) for user namespaces. The chart ships no node label for this and requires none. A node without the prerequisite refuses the pod at start, so the pool stays below its floor. This is documented kubelet behaviour, not measured here; it can be proved on a cluster only, and no such proof exists at this version. A project that wants to restrict the pool to prepared nodes sets `pool.node_selector` to a label of its own; the value reaches the node selector of every pod of the pool.

## Tests

`bash .github/scripts/test-sandbox-chart.sh` (offline: `helm template`, `yq`, `jq`) proves the checks that need no cluster.
